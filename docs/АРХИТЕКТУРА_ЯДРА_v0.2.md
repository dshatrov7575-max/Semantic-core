## 1. Назначение и граница

Ядро — общий язык данных шести продуктов: TechSense, Конфликтология, Web Monitoring, Dossier Analyser, Compliance Check, SemanticWiki. Версия v0.2 фиксирует модель данных и её правила в исполняемом виде: JSON Schema, реестр предикатов, нормативный валидатор, тестовый мир на все шесть продуктов, 205 векторов и мутационный прогон на 190 мутантов. Хранилища, интерфейсов, ингеста и ролей пользователей пока нет — это следующие шаги (§8).

Правило проекта: **правило, которое не проверяется кодом и не имеет негативного вектора, правилом не считается; условие правила, ослабление которого не ловит ни один вектор, считается непроверенным.**

## 2. Принятые решения

| № | Решение | Почему |
|---|---|---|
| D1 | Онтология и данные — первый слой платформы. CM18 заморожен как справочный документ слоя доверия. | Слою доверия без данных не к чему прикладываться (оценка готовности, 30.09.2026). |
| D2 | **Утверждение отдельно от сущности.** Сущность хранит только идентичность, всё остальное — утверждения (Claim) с доказательствами до фрагмента источника. | Досье, Проверка, страница вики и граф конфликта — проекции одних и тех же утверждений. Закрывает P1-005 TechSense. |
| D3 | **Адресация по содержимому.** `source_id` — sha256 байтов источника; `claim_id` и `receipt_id` — sha256 от RFC 8785 JCS (UTF-8) записи без собственного id. Профиль JCS целочисленный: деньги в копейках, доли в базисных пунктах, величины — десятичной строкой. | Неизменяемость и дедупликация. Целочисленный профиль убирает сериализацию float — источник расхождений в CM18 (R6-HR-06). |
| D4 | **Одна сущность в проекте — строго один раз.** Любой сильный идентификатор (ИНН, ОГРН, ОГРНИП, ИНН+КПП филиала, кадастровый номер, VIN, IMO, ключ события, тег оборудования) принадлежит одному владельцу. Идентификаторы слитого дубля остаются за выжившей сущностью, выведенной из оборота (RETIRED) — за ней самой. ФИО + дата рождения — слабый ключ: совпадение считается дублем, если у обоих нет различающихся ИНН (или разных пометок аналитика). Для сравнения имён и тегов строится «скелет»: NFKC, удаление невидимых символов, латинские двойники кириллических букв → кириллица, casefold, ё→е, любое тире → «-», кавычки удаляются, пробелы схлопываются. Кадастровые части сравниваются как числа. | Гарантия «через ключи, а не через договорённости». Проверка v0.1 показала, как латинская «o» в фамилии, U+200B, «""» вместо «»» и ведущий ноль в кадастровом номере давали второго человека или второй участок. |
| D5 | **Проверка — самостоятельный объект.** По одному лицу допускается сколько угодно Проверок разных профилей, они связаны цепочкой `previous_check_id`. Статус утверждения берётся на момент завершения Проверки по **системному времени записи** рецензии (`recorded_at`, его назначает хранилище), а не по заявленному `reviewed_at`. Каждое измерение завершённой Проверки, включая «не найдено», несёт след поиска: где и что искали, когда и кто, при наличии — источник с результатом. | Требование Compliance. Урок R6-HR-01 и OR-13: заявленное время подделывается задним числом. Без следа поиска фразу «сведений не выявлено» нечем подтвердить (OR-G2). |
| D6 | **Маркировки**: уровень (PUBLIC < INTERNAL < CONFIDENTIAL < RESTRICTED) и категории (PERSONAL_DATA, COMMERCIAL_SECRET, OFFICIAL_USE). Производное не шире ни одного входа: утверждение ≥ каждого источника, субъекта и объекта; Проверка ≥ субъекта и каждого утверждения. Категория PERSONAL_DATA обязательна у физлица, а на всё производное переходит через доминирование. | Правило CM18 «broader ACL forbidden» и 152-ФЗ. Проверка v0.1 нашла отчёт по физлицу с маркировкой PUBLIC (OR-05). |
| D7 | **TechSense и любой автоматический извлекатель — производители артефактов.** PIPELINE-утверждение входит ровно в один `ArtifactReceipt`, подписанный Ed25519. Ключи берутся **только из доверенного реестра** (`trust_anchors`): это конфигурация tenant вне данных, которые она удостоверяет. Ключ привязан к tenant и службе и действует в полуоткрытом интервале; отзыв учитывается. Утверждение может ссылаться на узел UMR-графа своего артефакта. | Проверка v0.1 показала, что ключ, лежащий в тех же данных, позволял любому «подписать» подложные показания TechSense (OR-02). Ссылка на узел графа доводит провенанс до графа (OR-G3). |
| D8 | **Одна нормативная реализация валидатора** (Python). Node используется только для JCS производителей на JS; совпадение проверяется тестом. | Урок R6-HR-06. |
| D9 | **Fail-closed.** Фаза 0 — сырые значения: только целые в пределах ±(2⁵³−1), без одиночных суррогатов (в том числе в ключах), без управляющих символов вне свободного текста. Фаза 1 — схема: шаблоны как полное совпадение, строгий календарь. Фаза 2 — семантика; любое непредвиденное исключение превращается в `VALIDATOR_INTERNAL_ERROR`, а не в «прошло». Без доверенного реестра и без байтов источников набор не проходит. | В v0.1 девять входов роняли валидатор, а байты источников в продакшен-форме не проверялись вовсе (OR-01, OR-06). |
| D10 | **Противоречие источников — предупреждение, а не ошибка.** Хранятся обе версии, отклонённые утверждения и непересекающиеся сроки противоречием не считаются. | Досье должно объяснять расхождение, а не терять одну из версий. |

| Слой | Содержание | Состояние |
|---|---|---|
| L0 Хранилище | Postgres (записи, индекс идентификаторов, ограничения, системное время) и объектное хранилище байтов по sha256 | план v0.3 (§8); Postgres 16 есть в рабочем окружении |
| L1 Онтология | 7 видов записей, 9 типов сущностей, 24 предиката, 35 кодов ошибок | **v0.2 исполнено** |

| L3 Производители смысла | TechSense (UD→UP→PropBank→AMR/UMR → утверждения + receipt); LLM-извлечение для Dossier и Compliance по тому же пути | контракт есть, производителей нет |
| L4 Разрешение сущностей | индекс идентификаторов, скелет имён, слияние | ручное, автоматического сопоставления нет |

| L6 Приложения | досье-проекция, отчёт Проверки, страница вики, граф конфликта, ответы с провенансом | нет |
| L7 Доверие (CM18) | реестры, леджер, кворумы, анти-rollback | справочно, заморожено; в v0.2 взят только реестр ключей |

## 4. Модель данных v0.2

| Вид | Идентичность | Ключевые поля | Главные правила |
|---|---|---|---|
| `Project` | `prj_…` | tenant, product (один из шести), маркировка по умолчанию | область видимости ссылок |
| `Source` | `src:sha256:<байты>` | tenant, вид (документ, статья, пост, выписка, **результат поиска в реестре**…), `observations[]`, `byte_length`; байты — в хранилище (`content_inline` допустим для демонстрации) | байты обязательны для проверки доказательств; хэш сверяется всегда; повторный сбор той же статьи — новая observation |
| `Entity` | `ent_…` | project; тип: PERSON, ORGANIZATION (юрлицо, **филиал**, неформальная группа), REAL_ESTATE, MOVABLE_PROPERTY, EVENT, CONFLICT, EQUIPMENT (экземпляр), **EQUIPMENT_MODEL** (тип), CONCEPT; identity по типу (у физлица возможен **ОГРНИП** для ИП); статус с `status_changed_at` | контрольные суммы ИНН-10/12, ОГРН, ОГРНИП, IMO; достаточность идентичности; уникальность (D4); корректность слияния |
| `Claim` | `clm:sha256:<JCS>` | subject, predicate, object (сущность или литерал), qualifiers, срок действия, evidence[] (источник, байтовый span, quote, quote_sha256, **узел графа**), produced_by, recorded_at, маркировка | domain, range, **схема идентификатора и единица величины по реестру**, квалификаторы; span подтверждается байтами и не режет символ UTF-8; маркировка ≥ входов |
| `ClaimReview` | `rev_…` | статус, reviewer, reviewed_at (заявлено), **recorded_at** (система) | claim.recorded_at ≤ reviewed_at ≤ recorded_at; порядок и неоднозначность — по recorded_at |
| `Check` | `chk_…` | субъект, профиль, as_of, статус, completed_at / **cancelled_at**, findings[] (измерение, результат, риск, утверждения, **searches[]**), overall_risk | §6 |
| `ArtifactReceipt` | `rcp:sha256:<JCS>` | producer, run_id, artifact_digest, версии схемы артефакта и семантического профиля, входы, выпущенные утверждения, issued_at, key_id, подпись | ключ — из доверенного реестра tenant; ровно один receipt на PIPELINE-утверждение |
| `trust_anchors` (вне набора) | `key_…` | tenant, служба, Ed25519, not_before ≤ t < not_after, revoked_at | ошибка реестра = `TRUST_CONFIG_INVALID`, ни одному ключу не доверяем |

## 5. Как шесть продуктов ложатся на ядро

| Продукт | Что использует | Особенность |
|---|---|---|
| TechSense | EQUIPMENT_MODEL (знание из инструкции о модели) и EQUIPMENT (установленный экземпляр), `ts.instance_of`, `ts.part_of`, `ts.has_parameter` (единицы из списка), `ts.requires_action`; PIPELINE + receipt + узел графа | версии схемы артефакта и семантического профиля в каждом receipt (P1-006) |
| Конфликтология | CONFLICT и EVENT (с местом), физлица, организации, неформальные группы; `conflict.party_to`, `conflict.influences` (явное или неявное; канал финансовый, политический, административный, медийный, правовой), `rel.affiliated_with` | субъекты влияния и их связи — утверждения с доказательствами |
| Web Monitoring | Source с многократными observations; `wm.mentioned` с тональностью | дедупликация по байтам (дедупликация публикаций — §9, O4) |
| Dossier Analyser | физлица (в том числе ИП), юрлица, филиалы, имущество; корпоративные и имущественные связи | уникальность, слияние дублей, расхождения источников как предупреждения |
| Compliance Check | Check, шесть измерений, след поиска, неретроактивность | многократные Проверки одного лица, в том числе после слияния его карточки |
| SemanticWiki | CONCEPT; `wiki.is_a`, `wiki.part_of`, `wiki.property` | проекция утверждений без Проверок |

## 6. Реестр правил (нормативный)

Фаза 0–1: `SCHEMA_INVALID` (сырые значения, схема, календарь); `TRUST_CONFIG_INVALID` (реестр доверия не по схеме, повтор ключа, неверный интервал — тогда не доверяем ни одному ключу).

| Код | Правило |
|---|---|
| DUPLICATE_ID | идентификатор записи уникален в наборе |
| REF_UNRESOLVED | каждая ссылка разрешается |
| CROSS_SCOPE_REFERENCE | сущности и утверждения — только своего проекта; источники — своего tenant |
| SOURCE_DIGEST_MISMATCH | байты (из данных или хранилища) совпадают с адресом и длиной; данные и хранилище не расходятся |
| SOURCE_CONTENT_UNAVAILABLE | у источника, на который ссылаются доказательства, есть проверенные байты |
| CLAIM_ID_MISMATCH / RECEIPT_ID_MISMATCH | id = sha256(JCS(запись без id [и подписи])) |
| IDENTIFIER_CHECKSUM_INVALID | ИНН-10, ИНН-12 (обе цифры), ОГРН, ОГРНИП, IMO |
| ENTITY_IDENTITY_INSUFFICIENT | организация РФ — ОГРН или ИНН; филиал — ИНН и КПП без ОГРН; неформальная — только название и disambiguator; иностранная — регистрационный идентификатор; физлицо без ИНН, ОГРНИП и даты рождения — disambiguator; автомобиль — VIN, судно — IMO; прочее имущество — любой идентификатор |
| ENTITY_DUPLICATE_IN_PROJECT | D4 |
| ENTITY_MERGE_INVALID | слияние только в существующую ACTIVE сущность того же типа и проекта |
| PREDICATE_UNKNOWN / DOMAIN_VIOLATION / RANGE_VIOLATION | предикат из реестра; тип субъекта; тип объекта или литерала, схема идентификатора, единица величины |
| QUALIFIER_INVALID | только объявленные квалификаторы; enum из списка; целое без bool и в диапазоне; строка не из пробелов; boolean — только bool; обязательные присутствуют |
| TEMPORAL_ORDER_INVALID | valid_from ≤ valid_to; источник получен не позже записи утверждения; claim.recorded_at ≤ reviewed_at ≤ review.recorded_at; закрытие Проверки не раньше запроса, as_of не позже закрытия; status_changed_at ≥ created_at |
| EVIDENCE_SPAN_INVALID | 0 ≤ start < end ≤ длина байтов; целые символы UTF-8; sha256 и quote совпадают |
| MARKING_BROADER_THAN_INPUT | D6 |
| MARKING_PD_MISSING | у физлица есть PERSONAL_DATA |
| CLAIM_REVIEW_AMBIGUOUS | нет двух разных статусов одного утверждения с одинаковым временем записи |
| CHECK_PROJECT_NOT_COMPLIANCE | Проверка только в проекте COMPLIANCE |
| CHECK_SUBJECT_INVALID | субъект — физлицо или юрлицо; ACTIVE, а у закрытой Проверки — ACTIVE либо слит/выведен **строго позже** её закрытия |
| CHECK_DIMENSION_OUTSIDE_PROFILE / CHECK_DIMENSION_MISSING | измерения только из профиля; у завершённой — все |
| CHECK_FINDING_INCONSISTENT | FOUND ⇔ есть утверждения; NOT_FOUND ⇒ риск NONE; без повторов; overall_risk = максимум |
| CHECK_SEARCH_MISSING | у завершённой Проверки каждое измерение имеет поиск в окне [запрос; завершение] |
| CHECK_CLAIM_NOT_ABOUT_SUBJECT | утверждение о субъекте или его слитом дубле, либо субъект — его объект |
| CHECK_CLAIM_DIMENSION_MISMATCH | предикат относится к измерению |
| CHECK_CLAIM_NOT_ACCEPTED_AT_COMPLETION | последний по времени записи статус на момент завершения — ACCEPTED |
| CHECK_PREVIOUS_INVALID | предыдущая Проверка — тот же субъект (с учётом слияний), строго более ранняя as_of |
| RECEIPT_KEY_INVALID | ключ есть в доверенном реестре, того же tenant и службы; not_before ≤ issued_at < not_after; не отозван к issued_at |
| RECEIPT_SIGNATURE_INVALID | подпись Ed25519 над receipt_id |
| RECEIPT_CLAIM_BINDING_INVALID | в receipt только PIPELINE-утверждения той же службы, run и проекта, записанные не позже issued_at, с источниками из входов и узлами графа этого артефакта; каждое PIPELINE-утверждение — ровно в одном receipt; у HUMAN-утверждения нет узла графа |
| VALIDATOR_INTERNAL_ERROR | страховка fail-closed; фаззинг (T4) требует, чтобы этот код не возникал |

Предупреждение `CONTRADICTION_SINGLE_VALUED`: у однозначного предиката два действующих (не REFUTED и не WITHDRAWN) утверждения с разными значениями и пересекающимся сроком, с учётом слияний.

## 7. Что доказано исполнением

Команды: `python3 tests.py` (около 3 минут) и `python3 mutants.py` (около 15 минут на двух ядрах). Окружение: Python 3.11, jsonschema 4.26, cryptography 46, Node 22.

| Тест | Результат |
|---|---|
| T1 тестовый мир: 85 записей (6 проектов, 13 источников, 24 сущности, 29 утверждений, 8 рецензий, 4 Проверки, receipt) + реестр доверия + хранилище байтов | 0 ошибок, 1 ожидаемое предупреждение |
| T2 векторы | 205: 179 негативных дают **ровно** свой набор кодов; 26 позитивных граничных чистые, у пяти дополнительно проверяются предупреждения |
| T3 покрытие | 35 из 35 кодов имеют негативный вектор |
| T4 фаззинг | 3000 случайных повреждений (seed фиксирован): 0 падений, 0 внутренних ошибок |
| T5 JCS | порядок ключей RFC 8785, экранирование, кириллица; отказ на float, 1.0, 2⁵³, одиночном суррогате в значении и ключе |
| T6 паритет JCS Python/Node | 16 386 значений без расхождений (все записи всех схемно-валидных наборов и специальные строки) |
| T7 командная строка | продакшен-форма (без content_inline, байты из каталога, ключи из файла доверия) проходит; без доверия и без байтов — отказ; float — отказ без трассировки |
| Мутационный прогон | 190 мутантов (каждый ослабляет или ужесточает одно условие): 187 убиты векторами, 3 эквивалентны с письменным обоснованием (M001, M005, M006 — защита в глубину; эквивалентность независимо подтверждена на 1 272 входах), 0 выживших |

Позитивные векторы проверяют строгость в обратную сторону: тёзки с разными ИНН, одноимённые митинги в разных городах, слияние субъекта после завершённых Проверок, ACCEPTED ровно в момент завершения, поиск ровно на границах окна, ключ ровно на not_before и за секунду до not_after, эмодзи целиком во фрагменте.

**Не доказано:** хранение и конкурентная запись; реальное назначение `recorded_at` хранилищем (в данных это пока поле, которое можно подделать; в срезе v0.3 его ставит БД); производительность; автоматическое разрешение сущностей; роли; реальный ингест и реальный TechSense; полнота реестра предикатов; межпроектная идентичность.

## 8. План вертикального среза (v0.3)

Цель: те же правила — **ограничениями базы данных**, а не только валидатором; одно досье и одна Проверка из реальных таблиц с провенансом каждого факта.

| Шаг | Что | Критерий приёмки |
|---|---|---|

## 9. Открытые вопросы

- **O1. Межпроектная идентичность.** Одна компания в четырёх проектах — четыре сущности. Предложение для v0.4: реестр идентичности уровня tenant («золотая запись»), проекты остаются изолированными по доступу.
- **O2. Персональные данные.** Сроки хранения и удаление исходников с ПДн (152-ФЗ) при неизменяемых адресах. Предварительно: каждый источник шифруется своим ключом, при удалении ключ уничтожается.
- **O3. LLM-извлечение для Dossier и Compliance** — как PIPELINE с receipt, так же как TechSense. Предварительно: да.
- **O4. Дедупликация публикаций Web Monitoring** (OR-G4): статья с одним лишним переводом строки сейчас — второй Source. Нужен объект «публикация» (канонический URL, дайджест нормализованного текста) над Source. Делать вместе с ингестом.
- **O5. Условия в TechSense** (OR-G3): `condition` пока свободный текст. Структурные условия — это задача P1-001 TechSense/MORSE (ACTION+OBJECT+[CONDITION]); в ядро они придут из неё, а не будут придуманы здесь.
