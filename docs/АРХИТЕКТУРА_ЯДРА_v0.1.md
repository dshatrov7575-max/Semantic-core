# Архитектура ядра v0.1 — TechSense Common Platform («Архитектура семантики»)

```text
DOC=АРХИТЕКТУРА_ЯДРА_v0.1
DATE=2026-09-30 МСК
AUTHOR=Главный-1
STATUS=PROPOSED (исполняемая часть проверена кодом, см. §7)
ONTOLOGY=core-ontology/0.1   PREDICATES=core-predicates/0.1   DATASET=core-dataset/0.1
```

## 1. Назначение и граница v0.1

Ядро — общий язык данных шести продуктов (TechSense, Конфликтология, Web Monitoring, Dossier Analyser, Compliance Check, SemanticWiki). v0.1 фиксирует **модель данных и её правила в исполняемом виде**: JSON Schema, реестр предикатов, нормативный валидатор, тестовый мир на все шесть продуктов и набор атакующих векторов. Хранилища, интерфейсов, ингеста и ролей пользователей в v0.1 нет — это следующие шаги (§8).

Правило проекта: **правило, которое не проверяется кодом и не имеет негативного вектора, правилом не считается.**

## 2. Принятые решения

| № | Решение | Почему |
|---|---|---|
| D1 | Онтология и данные — первый слой платформы. CM18 заморожен как справочный документ слоя доверия; к нему вернёмся, когда появится второй независимый оператор. | Слой доверия без данных, к которым он прикладывается, проверить нечем (оценка готовности от 30.09.2026). |
| D2 | **Утверждение отдельно от сущности.** Сущность хранит только идентичность; всё остальное — утверждения (Claim) с доказательствами до фрагмента источника. | Досье, Проверка, вики-страница, граф конфликта — проекции одних и тех же утверждений. Закрывает P1-005 TechSense (provenance до span). |
| D3 | **Адресация по содержимому**: `source_id = sha256(байты UTF-8)`, `claim_id` и `receipt_id` = sha256 от RFC 8785 JCS (UTF-8) записи без собственного id. Профиль JCS: только целые числа (деньги в копейках, доли в базисных пунктах, величины — десятичной строкой). | Неизменяемость, дедупликация и провенанс «бесплатно». Целочисленный профиль убирает единственную трудную часть JCS (сериализацию float) — источник расхождений в CM18 (R6-HR-06). |
| D4 | **Одна сущность в проекте — строго один раз** обеспечивается индексом идентификаторов: любой идентификатор (ИНН, ОГРН, кадастровый номер, VIN, ФИО+дата рождения…) принадлежит не более чем одной ACTIVE сущности проекта. Нормализация: NFKC, casefold, ё→е, схлопывание пробелов. Дубль не удаляется, а сливается (`MERGED → merged_into`). | «Через ключи, а не через договорённости». Слияние сохраняет историю и утверждения дубля. |
| D5 | **Проверка — самостоятельный объект.** Одно лицо — сколько угодно Проверок разных профилей; цепочка через `previous_check_id`. Статус утверждения в Проверке берётся **на момент её завершения** из append-only истории `ClaimReview`; позднее оспаривание не меняет завершённую Проверку, ретроактивное принятие не засчитывается. | Требование Compliance; урок R6-HR-01 (статус без истории нельзя проверить на момент наблюдения). |
| D6 | **Маркировки**: уровень (PUBLIC < INTERNAL < CONFIDENTIAL < RESTRICTED) + категории (PERSONAL_DATA, COMMERCIAL_SECRET, OFFICIAL_USE). Производное не шире входа: утверждение ≥ каждого источника, Проверка ≥ каждого утверждения. Физлицо и любое утверждение о физлице обязаны нести PERSONAL_DATA. | Правило CM18 «broader ACL forbidden» + 152-ФЗ. |
| D7 | **TechSense (и любой автоматический извлекатель) — производитель артефактов**: утверждение с `produced_by.kind=PIPELINE` обязано входить ровно в один `ArtifactReceipt`, подписанный Ed25519 ключом службы (`ServiceKey`, полуоткрытый интервал действия, отзыв). В receipt — `artifact_schema_version` и `semantic_profile_version`. Кворумов и свидетелей нет. | Правило 6 оценки готовности; закрывает P1-006 TechSense (версии схемы в каждом артефакте). |
| D8 | **Одна нормативная реализация валидатора** (Python). Node используется только для JCS (производители на JS); совпадение дайджестов проверяется тестом на всех записях. | Урок R6-HR-06: два «эталона», которые молча расходятся, хуже одного. |
| D9 | **Fail-closed**: сначала строгая схема и календарная корректность дат; при любой ошибке схемы семантические правила не запускаются. | Семантика на битых данных даёт ложные «прошло». |
| D10 | **Противоречие источников — не ошибка, а предупреждение** (`CONTRADICTION_SINGLE_VALUED`): хранятся обе версии со своими доказательствами. | Досье должно объяснять расхождения источников, а не терять одну из версий. |

## 3. Слои платформы: целевая картина и что есть сейчас

| Слой | Содержание | Состояние |
|---|---|---|
| L0 Хранилище | Postgres (записи, индекс идентификаторов, ограничения) + объектное хранилище (байты источников по sha256) | план v0.2 (§8); Postgres 16 доступен в рабочем окружении |
| L1 Онтология | 8 видов записей, 21 предикат, 32 правила | **v0.1 исполнено** |
| L2 Ингест | краулеры СМИ/соцсетей, коннекторы реестров, парсеры документов | нет |
| L3 Производители смысла | TechSense UD→UP→PropBank→AMR/UMR → утверждения + receipt; LLM-извлечение для Dossier/Compliance | контракт receipt есть, производителей нет |
| L4 Разрешение сущностей | индекс идентификаторов + MERGE | ручное; автоматического сопоставления нет |
| L5 Доступ | маркировки; роли, построчная безопасность, цели обработки | маркировки есть, ролей нет |
| L6 Приложения | досье-проекция, отчёт Проверки, страница вики, граф конфликта, ответы с провенансом | нет |
| L7 Доверие (CM18) | реестры, леджер, кворумы, анти-rollback | справочно, заморожено |

## 4. Модель данных v0.1

| Вид записи | Идентичность | Ключевые поля | Главные правила |
|---|---|---|---|
| `Project` | `prj_…` | tenant, **product** (один из 6), маркировка по умолчанию | область видимости всех ссылок |
| `Source` | `src:sha256:<байты>` | tenant, вид (документ, статья, пост, выписка…), `observations[]` (когда/откуда/кем получен), `byte_length`, `content_inline` (в тестах; в проде — объектное хранилище) | адрес = хэш содержимого; повторный сбор той же статьи = новая observation, не новая запись |
| `Entity` | `ent_…`, стабильный | project, тип (PERSON, ORGANIZATION, REAL_ESTATE, MOVABLE_PROPERTY, EVENT, CONFLICT, EQUIPMENT, CONCEPT), `identity` (схема по типу), статус ACTIVE/MERGED/RETIRED | контрольные суммы ИНН/ОГРН/IMO; достаточность идентичности; уникальность идентификаторов среди ACTIVE; корректность слияния |
| `Claim` | `clm:sha256:<JCS>` | subject, predicate, object (сущность или типизированный литерал), qualifiers, valid_from/valid_to, **evidence[]** (source, байтовый span, quote, quote_sha256), produced_by (HUMAN / PIPELINE), recorded_at, маркировка | domain/range/квалификаторы по реестру; span подтверждается байтами источника и не режет символ UTF-8; маркировка ≥ источников |
| `ClaimReview` | `rev_…` | claim, статус ACCEPTED/DISPUTED/REFUTED/WITHDRAWN, reviewer, reviewed_at | история только дописывается; два разных статуса в одну секунду запрещены |
| `Check` | `chk_…` | subject (ACTIVE физ/юрлицо), profile (EXPRESS_NEGATIVE, TENDERS_ONLY, SOCIAL_ONLY, FULL), as_of, статус, findings[] (измерение, FOUND/NOT_FOUND, риск, утверждения), overall_risk, previous_check_id | только в проекте COMPLIANCE; измерения строго из профиля и все — при завершении; утверждения о субъекте (или с ним в объекте), нужного измерения, ACCEPTED на момент завершения; overall_risk = максимум |
| `ServiceKey` | `key_…` | service, Ed25519 public key, not_before ≤ t < not_after, revoked_at | ключ своей службы, действует на момент выдачи receipt |
| `ArtifactReceipt` | `rcp:sha256:<JCS>` | producer (service, version), run_id, artifact_digest, artifact_schema_version, semantic_profile_version, входные источники, выпущенные утверждения, issued_at, key_id, signature | подпись над receipt_id; каждое PIPELINE-утверждение — ровно в одном receipt своего run; источники доказательств ⊆ входов |

Реестр предикатов (`predicates.json`) — данные, а не код: новые предикаты добавляются без изменения валидатора. Каждый предикат: domain, range, кардинальность (ONE/MANY), измерения Compliance, схема квалификаторов.

## 5. Как шесть продуктов ложатся на ядро

| Продукт | Что использует | Особенность |
|---|---|---|
| TechSense | EQUIPMENT; `ts.part_of`, `ts.has_parameter`, `ts.requires_action`; PIPELINE + receipt | утверждения из UMR-графа с версиями схемы и семантического профиля |
| Конфликтология | CONFLICT, EVENT, PERSON, ORGANIZATION (в т. ч. неформальные группы); `conflict.party_to`, `conflict.influences` (явное/неявное, канал: финансовый, политический, административный, медийный, правовой), `rel.affiliated_with` | субъекты влияния и их связи — утверждения с доказательствами |
| Web Monitoring | Source (статья, пост) с многократными observations; `wm.mentioned` с тональностью | дедупликация по содержимому |
| Dossier Analyser | PERSON, ORGANIZATION, REAL_ESTATE, MOVABLE_PROPERTY; корпоративные, имущественные связи; `competitor.competes_with` | уникальность сущности в проекте, слияние дублей, предупреждения о расхождении источников |
| Compliance Check | Check + измерения NEGATIVE, TENDERS, SOCIAL_MEDIA, CORPORATE, PROPERTY, COURT | многократные Проверки одного лица; неретроактивность статусов |
| SemanticWiki | CONCEPT; `wiki.is_a`, `wiki.part_of`, `wiki.property` | проекция утверждений без Проверок |

## 6. Реестр правил (нормативный)

Фаза 1 (схема): `SCHEMA_INVALID` — нарушение JSON Schema Draft 2020-12 или несуществующая календарная дата/время.

| Код | Правило |
|---|---|
| DUPLICATE_ID | идентификатор записи уникален в наборе |
| REF_UNRESOLVED | каждая ссылка разрешается |
| CROSS_SCOPE_REFERENCE | ссылки — только внутри проекта (сущности, утверждения) и внутри tenant (источники) |
| SOURCE_DIGEST_MISMATCH | source_id и byte_length соответствуют содержимому |
| CLAIM_ID_MISMATCH | claim_id = sha256(JCS(утверждение без claim_id)) |
| RECEIPT_ID_MISMATCH | receipt_id = sha256(JCS(receipt без receipt_id и signature)) |
| IDENTIFIER_CHECKSUM_INVALID | ИНН (10/12), ОГРН, IMO — контрольные цифры |
| ENTITY_IDENTITY_INSUFFICIENT | организация РФ — ОГРН или ИНН; неформальная — только disambiguator; физлицо без ИНН и даты рождения — disambiguator; ТС — VIN, судно — IMO |
| ENTITY_DUPLICATE_IN_PROJECT | идентификатор — не более одной ACTIVE сущности проекта |
| ENTITY_MERGE_INVALID | слияние только в ACTIVE сущность того же типа и проекта, не в себя |
| PREDICATE_UNKNOWN / DOMAIN_VIOLATION / RANGE_VIOLATION | предикат из реестра; тип субъекта и объекта/литерала по реестру |
| QUALIFIER_INVALID | квалификаторы — только объявленные, по типу и диапазону; обязательные присутствуют |
| TEMPORAL_ORDER_INVALID | valid_from ≤ valid_to; источник получен не позже записи утверждения; проверка утверждения не раньше его записи; Проверка завершена не раньше запроса, as_of не позже завершения; интервал ключа корректен |
| EVIDENCE_SPAN_INVALID | 0 ≤ start < end ≤ длина; фрагмент — целые символы UTF-8; sha256 и quote совпадают с байтами источника |
| MARKING_BROADER_THAN_INPUT | утверждение ≥ источников, Проверка ≥ утверждений |
| MARKING_PD_MISSING | физлицо и утверждения о физлице несут PERSONAL_DATA |
| CLAIM_REVIEW_AMBIGUOUS | нет двух разных статусов одного утверждения с одинаковым временем |
| CHECK_PROJECT_NOT_COMPLIANCE | Проверка только в проекте COMPLIANCE |
| CHECK_SUBJECT_INVALID | субъект — ACTIVE PERSON или ORGANIZATION |
| CHECK_DIMENSION_OUTSIDE_PROFILE | нет измерений вне профиля |
| CHECK_DIMENSION_MISSING | завершённая Проверка содержит все измерения профиля |
| CHECK_FINDING_INCONSISTENT | FOUND ⇔ есть утверждения; NOT_FOUND ⇒ риск NONE; измерение не повторяется; overall_risk = максимум |
| CHECK_CLAIM_NOT_ABOUT_SUBJECT | утверждение о субъекте (с учётом слияний) или субъект — его объект |
| CHECK_CLAIM_DIMENSION_MISMATCH | предикат утверждения относится к измерению |
| CHECK_CLAIM_NOT_ACCEPTED_AT_COMPLETION | для завершённой: утверждение записано до завершения и ACCEPTED на момент завершения |
| CHECK_PREVIOUS_INVALID | предыдущая Проверка — тот же субъект и проект, более ранняя as_of |
| RECEIPT_KEY_INVALID | ключ существует, принадлежит службе-производителю, not_before ≤ issued_at < not_after, не отозван на issued_at |
| RECEIPT_SIGNATURE_INVALID | Ed25519-подпись над receipt_id сходится |
| RECEIPT_CLAIM_BINDING_INVALID | каждое PIPELINE-утверждение ровно в одном receipt; совпадают служба, run, проект; записано не позже issued_at; источники доказательств ⊆ входов |

Предупреждение: `CONTRADICTION_SINGLE_VALUED` — у однозначного предиката (дата рождения, «входит в состав»…) два действующих утверждения с разными значениями и пересекающимся сроком (с учётом слияний).

## 7. Что доказано исполнением (30.09.2026)

Команда: `python3 fixtures.py && python3 tests.py` (Python 3.11, jsonschema 4.26, cryptography 46, Node 22).

| Тест | Результат |
|---|---|
| T1 тестовый мир: 77 записей (6 проектов, 11 источников, 21 сущность, 26 утверждений, 8 рецензий, 3 Проверки, ключ, receipt) | 0 ошибок, 1 ожидаемое предупреждение (дата рождения 1971 vs 1972, найдено через слитый дубль) |
| T2 векторы | 53: 50 негативных, каждый даёт **ровно** свой код; 3 позитивных граничных — чистые |
| T3 необходимость правила | для всех 50: при отключении целевого правила тот же набор данных проходит без ошибок |
| T4 покрытие | 32 из 32 кодов имеют вектор |
| T5 JCS | пример сортировки RFC 8785 §3.2.3, кириллица, экранирование, отказ на float/2^53/одиночный суррогат |
| T6 паритет JCS Python/Node | 4 164 записи всех наборов, расхождений 0 |

Векторы строятся генератором поверх **настоящего** мира и прогоняются **настоящим** валидатором; тестов, проверяющих сами себя или ищущих слова в тексте, нет.

**Не доказано** (честная граница): хранение и конкурентная запись; производительность; автоматическое разрешение сущностей; роли и построчный доступ; реальный ингест и реальный TechSense; полнота реестра предикатов (стартовый набор из 21); межпроектная идентичность (одна компания в четырёх проектах — четыре сущности).

## 8. План вертикального среза (v0.2)

Цель: те же правила — **ограничениями базы данных**, а не только валидатором; одно досье и одна Проверка из реальных таблиц с провенансом каждого факта.

| Шаг | Что | Критерий приёмки |
|---|---|---|
| S1 | DDL Postgres 16: projects, sources (+ ключ объекта по sha256), entities, **entity_identifiers** с частичным уникальным индексом `(project_id, scheme, value) WHERE status='ACTIVE'`, claims, claim_evidence, claim_reviews (append-only: запрет UPDATE/DELETE триггером), checks, check_findings, check_finding_claims, service_keys, artifact_receipts; внешние ключи, CHECK-ограничения | DDL применяется на чистой базе |
| S2 | Загрузчик: валидатор → транзакционная вставка; отказ всей пачки при любой ошибке | `world_valid.json` загружается; каждый из 50 негативных векторов отвергается (валидатором или БД), и для правил, продублированных в БД (уникальность, ссылки, проект Проверки, append-only), отказ БД доказан **в обход валидатора** |
| S3 | Проекции: досье (по правилам оформления владельца) и отчёт Проверки — каждое предложение с ссылкой на утверждение и фрагмент источника | для каждого факта в выводе находится span источника; расхождение дат рождения выводится с пояснением, а не одной датой |
| S4 | Адаптер TechSense: UMR-граф (упрощённый JSON) → утверждения + подписанный receipt | 3 утверждения по инструкции НС-2 проходят S2 |
| S5 | Web Monitoring: одна статья, полученная трижды | одна запись Source, три observations |
| S6 | Независимая атака на срез отдельным агентом | отчёт с ПРИНЯТО / ВОЗВРАТ |

## 9. Открытые вопросы (решение за Главный-1, владельцу — только при необходимости)

- **O1. Межпроектная идентичность.** Сейчас проекты изолированы. Предложение для v0.3: отдельный реестр идентичности на уровне tenant («золотая запись») со ссылками из проектных сущностей; проекты остаются изолированными по доступу.
- **O2. Хранение персональных данных.** Сроки и удаление исходников с ПДн (152-ФЗ) при неизменяемых адресах по содержимому — вероятно, шифрование каждого источника своим ключом и уничтожение ключа при удалении. Решение к v0.3.
- **O3. LLM-извлечение для Dossier/Compliance** — оформлять как PIPELINE с receipt, как TechSense (единый путь для любого автомата). Предварительно: да.
