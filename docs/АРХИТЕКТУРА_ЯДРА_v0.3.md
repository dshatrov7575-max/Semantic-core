## 1. Назначение и граница

Ядро — общий язык данных шести продуктов: TechSense, Конфликтология, Web Monitoring, Dossier Analyser, Compliance Check и SemanticWiki. Версия v0.3 состоит из двух исполняемых частей:

1. **Онтология 0.2.1.** JSON Schema, реестр предикатов, единственный нормативный валидатор, тестовый мир на все шесть продуктов, 242 вектора и 217 мутантов.
2. **Вертикальный срез S1/S2 на PostgreSQL 16.** Правила онтологии стали ограничениями и триггерами базы. Ключи идентичности база вычисляет сама. Живая роль приложения имеет минимальные права. Все правила атакуются в обход валидатора.

Пока нет: проекций (досье, отчёт Проверки — шаг S3), адаптера TechSense, ингеста, объектного хранилища, интерфейсов и ролей пользователей.

Правило проекта: **правило без кода и без негативного вектора правилом не считается. Условие, ослабление которого не ловит ни один вектор, считается непроверенным. Правило, заявленное «в базе», должно выдерживать атаку в обход валидатора.**

## 2. Принятые решения

Решения D1–D10 версии v0.2 действуют. Ниже они приведены кратко; изменения v0.3 выделены.

| № | Решение |
|---|---|
| D1 | Онтология и данные — первый слой. CM18 заморожен как справочный документ слоя доверия. |
| D2 | Утверждение отдельно от сущности. Сущность хранит только идентичность, всё остальное — утверждения с доказательствами до байтового фрагмента источника. |
| D3 | Адресация по содержимому: `source_id` = sha256 байтов; `claim_id` и `receipt_id` = sha256(RFC 8785 JCS) без собственного id. Профиль JCS целочисленный. |
| D4 | **Одна сущность в проекте — строго один раз. v0.3: ключ идентичности двухуровневый.** **Точный ключ** (NFC, удаление всех Default_Ignorable и Cf, свёртка полной ширины, casefold, тире → «-», без кавычек, схлопнутые пробелы): совпадение = ошибка. **Скелет** (плюс NFKC, латинские и греческие двойники → кириллица, ё→е): совпадение = ошибка для людей, организаций, событий, конфликтов и моделей оборудования, но только предупреждение `POSSIBLE_DUPLICATE` для тегов оборудования и понятий. PT-101 и РТ-101 по ГОСТ — разные приборы, «небо» и «нёбо» — разные понятия. Необязательный различитель (место события, пометка аналитика) разводит сущности, **только если он есть у обеих сторон и различается**. Тёзок разводят и ИНН, и ОГРНИП. В индексе ключ несёт тип сущности. |
| D5 | Проверка — самостоятельный объект, по одному лицу их сколько угодно. Статус утверждения берётся на момент завершения по системному времени записи рецензии. У каждого измерения есть след поиска. **v0.3: у закрытой Проверки субъект может быть слит или выведен из оборота только строго после закрытия.** |
| D6 | Маркировки: производное не шире ни одного входа. **v0.3: к входам Проверки относятся и источники результатов поиска.** |
| D7 | Производители артефактов подписывают receipt Ed25519. Ключ — только из доверенного реестра, **уникальный в пределах tenant**. Сломанная запись одного tenant не отключает ключи другого. |
| D8 | **Разделение ответственности валидатора и базы (уточнено в v0.3):** |
|  | — только нормативный валидатор (Python): JCS-адреса, подпись Ed25519, квалификаторы, строгая схема и фаза 0, контрольные суммы литералов утверждений, схемы идентификаторов и единицы величин; |
|  | — база сама: ключи идентичности (**вычисляются из `identity` SQL-портом нормализации, паритет с валидатором проверяется тестом**), контрольные суммы ИНН, ОГРН, ОГРНИП и IMO у сущностей, достаточность идентичности, границы проекта и tenant, неизменяемость, системное время, доказательства по байтам, маркировки, правила Проверки, привязка receipt к подписанному телу. |
| D9 | Fail-closed: фаза 0 итеративна с пределом вложенности 64; ни одно исключение не превращается в «прошло». |
| D10 | Противоречие источников — предупреждение, а не ошибка. **v0.3: второй код предупреждения — `POSSIBLE_DUPLICATE`.** |

## 8. Срез S1/S2 на PostgreSQL 16

Файлы среза: `ddl_s1.sql`, `keys_s1.sql`, `casefold_s1.sql`, `load_s1.py`, `attacks_s1.py`, `regression_rs_db_attacks.py`, `db_vectors_s1.py`, `keys_parity_s1.py`, `gen_casefold_s1.py`.

**Устройство.**

1. **Загрузчик.** Сначала нормативный валидатор (fail-closed). Затем одна транзакция под ролью `ac_migrator` в режиме исторического импорта; реестр доверия пишет роль `ac_trust_admin`.
2. **Роли.**
   - Приложение входит как `ac_app`. Это член только `ac_loader`: стать `ac_migrator` он не может.
   - У `ac_loader` права минимальные: INSERT в таблицы данных (все они append-only). UPDATE разрешён только в двух местах: колонки статуса у сущностей и колонки статуса и итога у Проверок.
   - Права на `entity_keys` и `claim_evidence`, реестры, проекты и TEMP у приложения нет.
3. **Ключи идентичности** выводит сама база из `identity` триггером: SQL-порт `base_key`, `skel`, `id_norm`, `tag_norm` и `entity_identifiers` плюс контрольные суммы. Регистр сворачивается по таблице, сгенерированной из Python `str.casefold()`.
4. **Системное время.** В живом режиме `recorded_at`, `reviewed_at` и `recorded_at` рецензий, `status_changed_at`, `created_at`, `requested_at`, `completed_at` и `cancelled_at` ставит база. Для записей, адресуемых по содержимому, база отвергает время вне окна [now − 5 мин; now]. Историческое время разрешено только `ac_migrator` и никогда не в будущем.
5. **Проверка при COMMIT** (отложенные триггеры):
   - полнота Проверки: измерения профиля, FOUND ⇔ утверждения, итоговый риск, след поиска в окне;
   - для завершённой Проверки заново: статус каждого утверждения на момент завершения, отношение к субъекту, доминирование маркировок;
   - ровно один receipt на PIPELINE-утверждение; строки receipt совпадают с подписанным телом.

**Доказательства.**

| Проверка | Результат |
|---|---|
| Загрузка эталонного мира | `LOAD: OK` — 6 проектов, 13 источников, 24 сущности, 33 ключа, 29 утверждений, 32 доказательства, 8 рецензий, 4 Проверки, 1 receipt |
| Паритет ключей база ↔ валидатор | мир: 33 строки совпали; все 99 различных сущностей из всех векторов — 0 расхождений; 4 × 3000 враждебных строк (невидимые символы, двойники латиницы, греческого, армянского и кириллицы, полная ширина, NFKC, тире, кавычки, пробелы Unicode, İ, ß, ﬁ) — 0 расхождений |
| Атаки в обход валидатора (`attacks_s1.py`) | **69 из 69** отклонены именно целевым правилом, **5 из 5** законных операций проходят (новое утверждение «сейчас», рецензия с «задним» временем → системное, ещё одна Проверка того же субъекта, слияние нового дубля с переносом ключей, 33/33 цитат подтверждаются байтами) |
| Атаки ревьюера (`regression_rs_db_attacks.py`, копия его `db_attacks.py`) | все атаки уровня P0 отклоняются: D01, D02, D03 (ключи идентичности), D05 (подмешивание доказательства), D06 (маркировка источника), D09, D10 (завершение Проверки). Отклоняются и P1: D07, D08, D11–D16, D21, D22 (гонка слабых ключей — блокировка по ключу). Остаток — ниже |
| Покрытие векторов базой (`db_vectors_s1.py`) | из **206** негативных векторов база **без валидатора** отвергает **168** (82 %), 32 остаются только на валидаторе (по D8), 6 непредставимы в UTF-8/SQL |

**Остаток атак ревьюера** (скрипт считает находкой любой коммит):
- **D17, D17b, D23 — удержано.** Запись прошла, но база подменила заявленное «будущее» время системным. Проверено запросом: `created_at` и `cancelled_at` равны now().
- **D18 — принятое решение (P2).** Окно в 5 минут для времени, входящего в хэш, — это допуск на расхождение часов.
- **D19 — артефакт харнесса (P1).** В тестовом наборе сессия суперпользователя. В эксплуатации приложение входит как `ac_app` и стать `ac_migrator` не может; контроль D19b подтверждает.
- **D20 — открыто (P2).** Окно исторического импорта у `ac_migrator` не ограничено.
- **D04, D04b — открыто (P1, RS-15).** Если неквалифицированная запись уже есть, омоним или тёзку нельзя добавить: к существующей сущности нельзя дописать пометку. Решение в S3: операция «уточнить идентичность», которая создаёт новую версию сущности со слиянием.

**Только на валидаторе** (32 вектора, по D8):
- JCS-адреса и подпись (3);
- квалификаторы (9);
- строгая схема и фаза 0 (14);
- контрольные суммы литералов (2);
- схема и единица литерала (2);
- структура файла доверия (2).

## 11. Две линии работ 30.09 и их сведение

30.09 параллельно шли две линии.
- **Утренняя (эта).** Ядро v0.1 → v0.2 с независимыми проверками. На Drive оно не выгружалось.
- **Дневная.** Отдельное ядро «v0.1» в папке ЯДРО/ЯДРО_v0.1 на Drive: 68 записей, 18 правил, срез S0 на PostgreSQL, собственное независимое ревью с вердиктом ВОЗВРАТ (ONT-01…23).

Основной считается утренняя линия: она прошла две проверки и зрелее. Дневная линия сохранена как архив. Её полезные результаты перенесены сюда:
- подход «правила как ограничения PostgreSQL» и атаки на уровне БД;
- находки ONT-01 (маркировка Проверки ≥ утверждений: в v0.2 было в валидаторе, теперь и в БД) и ONT-03 (неизменяемый провенанс в БД);
- ONT-06 и ONT-07 (время ставит система);
- урок ONT-23 (`$` перед `\n`: в v0.2 закрыт как OR-04).
