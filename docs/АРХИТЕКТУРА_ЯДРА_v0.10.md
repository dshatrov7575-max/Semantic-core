## 2. Изоляция и блокировки (`slice/ddl_s1.sql`, `ddl_s9.sql`, `ddl_s5.src.sql`, `ddl_s11.sql`)

**Почему.** Стражи ядра устроены как «взять блокировку по ключу — затем прочитать состояние». В REPEATABLE READ и
SERIALIZABLE снимок берётся до блокировки, и страж читает устаревшее. Проверка цикла 11 показала это на деле: два
физлица с одним ФИО и датой рождения фиксировались оба, если писать их в REPEATABLE READ.

**Правило.** Любая запись в таблицы ядра вне READ COMMITTED отвергается: `ISOLATION_LEVEL_UNSUPPORTED`.
- `ac.require_read_committed()` вызывается всеми функциями блокировки (`ac.lock_keys`, `ac.lock_keys_shared`,
  `ac.lock_entities`) и прямыми местами советующих блокировок;
- триггер уровня оператора `a_isolation_guard` стоит на каждой таблице схем `ac`, `ac_trust` (41 таблица, цикл в
  `ddl_s11.sql`, применяется последним) и на каждой таблице строк набора (ставится в `ac.dataset_open`);
- чтение в любом уровне разрешено. Исключение: проекции, которые сами берут блокировку (`ac.custody`, `ac.model`,
  `ac.schema_gaps`), вне READ COMMITTED отвергаются тем же кодом.

**Ключи `entity:`** (`ac.lock_entities`):
- ИСКЛЮЧИТЕЛЬНО ключ берёт только то, что меняет саму сущность: её слияние или вывод из употребления, вставка сразу
  слитой, решение об её идентичности (DISTINCT, QUALIFY);
- РАЗДЕЛЯЕМО — всё, что опирается на её состояние: утверждение о ней, Проверка (открытие, строки, закрытие), слияние В неё;
- слияния в одну цель идут по одному — отдельный исключительный ключ `merge-into:<цель>`, берётся раньше `entity:`.

Следствие: два писателя, опирающихся на одну сущность, друг друга не ждут и не блокируют взаимно. **Названное
ограничение:** взаимная блокировка (`deadlock detected`, 40P01) остаётся возможной для транзакции с несколькими записями
о сущностях. Два найденных рецензией сценария: (1) транзакция сначала опирается на сущность, а затем меняет её
(утверждение о X и решение об идентичности X); (2) два сеанса сливают по две сущности в цели T и U в противоположном
порядке. Целостность не страдает; **загрузчик обязан повторять транзакцию, отвергнутую с 40P01**.

**Закрытые гонки прежних стражей** (все найдены независимой рецензией, все воспроизводились в READ COMMITTED):

| Что фиксировалось | Исправление |
|---|---|
| утверждение о сущности после её слияния | `ac.claims_before` берёт разделяемые `entity:` субъекта и объекта |
| цепочка слияний D→A→B (вставка сразу слитой) | вставка MERGED берёт ключи |
| пара и слита, и решена «различны» | отложенная проверка DISTINCT берёт `entity:` обеих |
| «различны» в обход двумя слияниями в одну цель | ключ `merge-into:` |
| уточнение (QUALIFY) сливаемой сущности | ветка QUALIFY берёт `entity:` |
| открытая публикация с закрытым рендерингом её текста | ключ `text:tenant/digest` у публикации, прихода байтов и нового триггера на наблюдение (`ac.rendition_check`) |
| утверждение и удаление его предиката из схемы в одну секунду | версия определения — строго позже последнего утверждения схемы tenant (`ac.schema_claims_max`) |

**Новое правило: субъект открытой Проверки — ACTIVE.** Слияние и вывод из употребления сущности, по которой открыта
Проверка, отвергаются (`CHECK_SUBJECT_INVALID`): сначала Проверку закрывают или отменяют. Раньше база это принимала,
а валидатор такой мир отвергал.

## 3. «О ком строка» (D27.3)

**Нормальная форма идентификатора строки.** Значение ячейки с `identifier_scheme` сравнивается с ключом сущности в той
форме, в какой ключ хранится (`row_id` в валидаторе, `ac.row_id` в базе):
- национальные номера (`ru.inn`, `ru.ogrn`, `ru.ogrnip`, `vin`, `imo`) — как записаны;
- кадастровый номер — без ведущих нулей, если он по форме (цифры и двоеточия); иначе как записан;
- прочие схемы — без регистра и разделителей (`id_norm`);
- значение с символом, не назначенным в Юникоде валидатора (14.0), — как записано (PostgreSQL нормализует по более
  новой версии Юникода; иначе стороны расходятся);
- прочерк и пустая строка — не идентификатор (в реестрах это заглушка).

У сущности отвергаются (`ENTITY_IDENTITY_INSUFFICIENT`, валидатором и базой одинаково): идентификатор с пустой нормальной
формой; identity с символом, не назначенным в Юникоде валидатора, **в любом строковом поле** (название, ФИО, метка,
идентификаторы) — все ключи строятся нормализацией, а она у валидатора (Юникод 14.0) и PostgreSQL (более новый) для
таких символов разная. То же — уточнение решения QUALIFY (место, disambiguator): оно входит в слабый ключ. Поэтому ни
ключ сущности, ни его квалификатор неназначенных символов не содержат.

**Конфликт сильных ключей** (строка называет одну сущность, в проекте её идентификаторы у двух): это состояние
проекта, а не дефект утверждения — оно возникает и после записи утверждения и снимается слиянием. Первая редакция
отвергала запись; рецензия показала три обхода (порядок записи, выбор времени, исторический импорт). Теперь:
- валидатор: предупреждение `ROW_SUBJECT_CONFLICT` (по нынешнему состоянию мира; владельцы ключа — выжившие после слияний);
- база: запись принимается; при чтении у доказательства поле `subject_conflict: true`. Считается по допуску
  **читателя**: сущность, которую читатель видеть не вправе, не учитывается. Сеанс без допуска в проекте: владелец
  базы (суперпользователь) видит все конфликты, как валидатор; для прочих ролей в `ac.conflict_clearance` записан
  ответ по маркировке утверждения, но достичь его нельзя: через проекции такая роль получает `ACCESS_DENIED`, прямой
  вызов `ac.evidence_json` ей запрещён;
- `ac.dataset_subject(проект, версия, ключ)` → `NONE` / `ONE` / `CONFLICT` / `SEVERAL_TYPES` (владельцы разных типов:
  компания и прицеп с одним номером — не конфликт) со списком владельцев, видимых читателю.

## 4. Актуальность строки (`ac.row_currency`, поле `currency` у доказательства-строки)

Проекция идёт от версии утверждения по цепочке `previous` к последней запечатанной версии и отвечает:

| Статус | Смысл |
|---|---|
| `CURRENT` | следующих версий нет |
| `NOT_LOADED` | следующая версия зарегистрирована, строки не загружены |
| `UNCHANGED` | строка та же (по хэшу строки) |
| `CHANGED` + `changed_columns` | изменились процитированные колонки (названы те, чью маркировку в новой версии покрывает маркировка утверждения — не допуск читателя) |
| `CHANGED_ELSEWHERE` | строка изменилась, процитированное — нет |
| `ABSENT` | строки с этим ключом нет (у набора без ключа — и изменённая строка: её можно найти только по хэшу) |
| `INCOMPARABLE` | у новой версии другой ключ (колонки или типы) |
| `BRANCHED` | у версии две следующих: «последняя» не определена |

Версия, маркированная выше утверждения, не называется и не учитывается, но цепочка через неё проходит: иначе ответ
«следующих версий нет» был бы неверным при доступной читателю более новой версии. **Раскрывается намеренно:** связь
«версия 3 следует за версией 1» (из неё читатель может вывести, что между ними есть закрытая версия). Содержание и имя
закрытой версии не раскрываются. Значений ячеек проекция не возвращает.

**Названные ограничения:** ответ на момент ближе пяти минут к «сейчас» помечен предварительным (`provisional`), как всё
в проекциях; время печати версии ставится в конце печати, поэтому транзакция загрузчика после печати должна быть короче
пяти минут (S11R-13).

## 5. Исследование: общие файлы между версиями (`research/ИССЛЕДОВАНИЕ_2026-10-03_дельты_версий.md`)

Проект D27.2 утверждает: «новая версия ссылается на неизменившиеся файлы по хэшу — дельты ЕГРЮЛ не множат объём».
Модель на 1 млн строк (`research/dataset_delta_bench.py`) показала: **при файлах по 4096 строк и 0,1 % изменённых
строк общих файлов практически нет** (1–2 %). Общие файлы появляются только при мелких файлах (64 строки: 88–94 %) и
устойчивой резке (по корзинам хэша ключа или с границами по содержимому); для 8 млн строк это 125 тыс. файлов — больше
нынешнего предела манифеста (100 000).

Выбор за владельцем: (а) полные версии, как сейчас; (б) мелкие файлы + двухуровневый манифест; (в) версии-дельты с
доказательством невхождения (новый формат). Рекомендация Главного-1 — (а) до настоящих данных.
