## 1. Что это и где граница

Ядро — общий язык данных шести продуктов. В v0.7 добавлено **объектное хранилище оригиналов** (S5, часть 2,
решение D26) — последнее, что было отмечено «пока нет» в v0.6:

1. **Онтология 0.2.6** — правило `ORIGINAL_INVALID` (40-й нормативный код), 366 векторов, 320 мутантов.
2. **Срез на PostgreSQL 16** — реестр `ac.objects`/`ac.object_checks`, роль `ac_gateway`, проекция «сохранность
   оригиналов» `ac.custody`.
3. **Объектное хранилище** — слой `store/` (вне ядра): адресация сырых оригиналов (страница, PDF, скан) по
   `sha256`, S3-совместимый клиент (AWS SigV4, stdlib + requests) поверх `FsBackend`/`S3Backend`, шлюз
   `store/gateway.py` — единственный, кто пишет реестр.
4. Всё из v0.6 без изменений: публикации Web Monitoring (S5 ч.1), адаптер TechSense (S4), проекции досье/отчёта
   Проверки/провенанса/карточки оборудования/ленты упоминаний.

Пока нет: идентификаторов СНГ (S6, следующий цикл), досье в .docx, ролей пользователей в интерфейсах, реальных
данных TechSense и Web Monitoring (папки `ВХОДНЫЕ_ДАННЫЕ/TechSense` и `ВХОДНЫЕ_ДАННЫЕ/Web_Monitoring` пусты),
проверки на настоящем S3/MinIO (см. §7).

## 2. Новые решения

| № | Решение |
|---|---|
| **D26** | **Объектное хранилище оригиналов.** Источник хранит ТЕКСТ в базе (как раньше); наблюдение МОЖЕТ сослаться на сырой оригинал — `{object: "sha256:…", media_type, byte_length}` — физически лежащий в S3-совместимом хранилище, адресованный содержимым. Претензия на сохранность проверяется дважды: (1) валидатором — байты по этому адресу есть, длина и хэш совпадают (`ORIGINAL_INVALID`); (2) базой — объект **регистрируется только вместе с успешной проверкой чтением, в одной транзакции**, пишет это исключительно роль `ac_storage` через LOGIN-роль `ac_gateway` (`store/gateway.py`), никогда приложение напрямую. Скрубер (`gateway.scrub`) периодически перечитывает каждый объект и дописывает в неизменяемый журнал `ac.object_checks` результат (`OK`/`MISSING`/`CORRUPT`) сразу после чтения ЭТОГО объекта — не пачкой в конце обхода (иначе время в журнале лжёт, S6R-08). Хранилище НИЧЕГО не чинит и не удаляет: восстановление — операторское (из резервной копии), следующий скруб это видит и записывает. |
| **D26.1** | **Проекция «сохранность оригиналов»** `ac.custody(claim, as_of)` (`custody/0.1`): для каждого источника, на который опирается утверждение, — его ПЕРВОЕ наблюдение (как провенанс, D15: не полный список заборов — не-первые заборы могут принадлежать работе другого проекта, S6R-03) и его оригинал — тип, размер, когда сохранён, состояние по последней проверке на момент `as_of` и сколько раз проверялся. Сериализуется с каждым писателем, который мог бы ещё изменить ПРОШЛЫЙ ответ, через те же ключи advisory-блокировок, что берут `ac.objects`/`ac.object_checks`/`ac.source_observations` перед вычислением своего времени (`'object:'`, `'source:'`) — тот же приём, которым D14/D22 защищают закрытие Проверки и публикации. **Важно (см. §6): функция НЕ `STABLE`** — в PostgreSQL `STABLE`-функция не берёт свежий снимок для своих ЖЕ внутренних операторов после ожидания на блокировке, из-за чего первая версия проекции отвечала по снимку ДО блокировки, то есть не видела того самого события, которого дожидалась. |
| **D26.2** | **Исторический загрузчик — тот же путь, что и живая запись.** `slice/load_s1.py` не вставляет строки реестра сам (это была бы заявка приложения «я сохранил», без хранилища вообще, S6R-07) — он вызывает `gateway.register(store, tenant, content[addr], media_type)` для каждого оригинала эталонного мира, через одноразовое локальное хранилище: запись — чтение обратно — сверка хэша — регистрация, как и в проде. |

## 4. Проекция «сохранность оригиналов» (`slice/ddl_s5b.sql`, `ac.custody`)

`ac.custody(claim, as_of)`: для утверждения — текст на момент `as_of`, маркировка, и по каждому источнику
доказательства (с проверкой допуска и видимости, как у провенанса, D15) — его первое наблюдение и, если оно
ссылается на оригинал: адрес, тип содержимого, заявленная длина, когда сохранён, состояние по последней проверке
на момент `as_of` (`OK`/`MISSING`/`CORRUPT`/`UNCHECKED`) и число проверок к этому моменту. Отказ без допуска и
для неизвестного/нечитаемого на `as_of` утверждения — один и тот же `ACCESS_DENIED`. Доказательство (цитата из
текста) не зависит от судьбы оригинала: утраченный или повреждённый оригинал не мешает проверить цитату по
тексту в базе — оригинал удостоверяет *сохранность исходной формы*, а не сам факт. Рендер — `slice/render_s5b.py`,
образец — `ПРИМЕР_СОХРАННОСТИ_S5.md`.

## 6. История проверки S6 и разбор корневой причины S6R-01/02

| Этап | Вердикт | Главное |
|---|---|---|
| Первый проход | (A) С ЗАМЕЧАНИЯМИ; (B) **ВОЗВРАТ**; (C) **ВОЗВРАТ** | P0 S6R-01/02: ответ `ac.custody` на ПРОШЕДШИЙ момент менялся задним числом при поздней фиксации проверки/наблюдения; P1 S6R-03/04/05/06/07: custody раскрывала чужие заборы, гонка проверка↔наблюдение, ошибки хранилища журналировались как «утрачен», шлюз работал сеансом суперпользователя, исторический загрузчик заявлял несуществующую проверку; P2 S6R-08…12 |
| Исправление, 1-й проход | — | добавлены advisory-блокировки (`ac.lock_keys`) перед чтением в `ac.custody`, по тем же ключам `'source:'`/`'object:'`, что берут писатели — приём по аналогии с D14/D22. Собственные тесты (`s5b_tests.py`, `attacks_s5b.py`, `store_tests.py`) — PASS |
| **Расхождение, обнаруженное при повторном прогоне скриптов рецензента** | — | `db_attacks.py` A1 **по-прежнему** показывал «FINDING — тот же `as_of`, разный ответ», хотя блокировка подтверждённо срабатывала (`pg_locks`: сеанс custody держит один ключ и ждёт именно тот, что держит писатель). Корень найден изолированным прогоном: минимальная функция «взять блокировку → отдельным оператором прочитать» ведёт себя правильно (свежий снимок после ожидания) ТОЛЬКО если функция **не** помечена `STABLE`. PostgreSQL для `STABLE`-функции переиспользует снимок, взятый для вызывающего запроса, и НЕ берёт свежий для её собственных внутренних операторов — свойство, которое не описано явно в документации про блокировки, но воспроизводится устойчиво: один и тот же код «блокировка → `jsonb_build_object` с вложенным `STABLE SQL`-помощником» даёт свежие данные как `VOLATILE` и устаревшие — как только добавлена `STABLE`, независимо от формы чтения (прямой `SELECT`, обёртка в JSON, вложенная функция, одна или две блокировки). `ac.custody` была объявлена `STABLE`; все триггеры-стражи (`observation_original_guard` и др.), использующие тот же приём, — обычные `VOLATILE`-функции по умолчанию, поэтому у них проблемы не было. **Исправление: убрать `STABLE` у `ac.custody`** (она и так вызывается только как отдельный верхнеуровневый оператор, никогда не вложена в другую функцию — терять от этого нечего) |
| Переисправление + полная переповерка | — | `db_attacks.py` A1/A2 → **held**; остальные находки (A3–A9, C1–C4, B1–B8, store_attacks2, val_attacks, val_mutants) передержаны тем же набором скриптов на свежих базах; S6R-12 (единственная ранее открытая P2 в области A) закрыта тремя новыми векторами (N704: плохой оригинал у ВТОРОГО наблюдения; N705: заявленная длина БОЛЬШЕ фактической; N706: источник без текста в хранилище) и тремя мутантами (M703–M705 в `core/mutants.py`) — `val_mutants.py` теперь показывает R1–R4 все KILLED |
| Финально | **ПРИНЯТО** | все 12 замечаний закрыты и переподтверждены; открытых находок по S6 нет (остались только заранее известные ограничения среды, §7) |
