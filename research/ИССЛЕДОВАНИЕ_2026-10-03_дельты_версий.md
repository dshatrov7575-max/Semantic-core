# Исследование 03.10.2026: берёт ли новая версия набора файлы предыдущей «по хэшу»

Вопрос к проекту D27.2: «новая версия ссылается на неизменившиеся файлы по хэшу (дедупликация, дельты ЕГРЮЛ не множат
объём)». Проверено моделью `research/dataset_delta_bench.py` (вывод — `research/dataset_delta_bench.out`), 1 млн строк.

Файл версии неизменен, только если в нём те же строки с теми же значениями. Доля ФАЙЛОВ, которые новая версия берёт у
предыдущей без перезаписи (среднее по 5 зёрнам; в скобках — доля СТРОК, если она заметно меньше):

| Изменено / добавлено / удалено строк | Резка | Файл 4096 строк (как в цикле 10) | Файл 512 строк | Файл 64 строки |
|---|---|---|---|---|
| 0,1 % / 0 / 0 | подряд по ключу | 1 % | 60 % | 94 % |
| 0,5 % / 0 / 0 | подряд по ключу | 0 % | 7 % | 73 % |
| 1 % / 0 / 0 | подряд по ключу | 0 % | 0,5 % | 53 % |
| 0,1 % / 0,05 % / 0,05 % | подряд по ключу | 0 % | 0,6 % | 1,6 % |
| 0,1 % / 0,05 % / 0,05 % | по корзинам хэша ключа | 0 % | 36 % | 88 % |
| 0,1 % / 0,05 % / 0,05 % | границы по содержимому | 11 % (строк 1 %) | 51 % (26 %) | 89 % (79 %) |
| 0,01 % / 0,005 % / 0,005 % | по корзинам | 45 % | 91 % | 99 % |
| 0,01 % / 0,005 % / 0,005 % | границы по содержимому | 55 % (29 %) | 91 % (83 %) | 99 % (98 %) |

Числа для корзин совпадают с аналитикой (1−u−a−d)^C: файл цел, если не тронута ни одна из его C строк.

Исправление после независимой рецензии (S11R-16): в первой редакции число корзин округлялось до степени двойки вниз,
корзины выходили почти вдвое крупнее заявленного размера файла, и числа для корзин были занижены (15 % вместо 36 %,
20 % вместо 45 %); таблица считалась по одному зерну. Модель исправлена, добавлена третья резка — границы по содержимому.

Выводы:
1. При файлах по 4096 строк и изменениях, разбросанных по реестру (так меняется ЕГРЮЛ), **общих файлов между версиями
   практически нет** уже при 0,1 % изменённых строк — при любой резке. Утверждение проекта в этом виде не выполняется.
2. Резка «подряд по ключу» ломается от одной вставки или удаления: сдвигаются все следующие файлы. Устойчивы две резки:
   по корзинам хэша ключа и с границами по содержимому (файл кончается на строке, у которой хэш ключа делится на C).
   Вторая сохраняет порядок строк по ключу — он нужен для доказательства невхождения из варианта (в); её цена — файлы
   разного размера: крупные задеваются чаще, поэтому доля общих СТРОК ниже доли общих файлов.
3. Чтобы файлы действительно были общими, нужны маленькие файлы (≈64 строки): для 8 млн строк это ≈125 тыс. файлов и
   манифест ≈25 МБ на версию. **Это больше нынешнего предела манифеста — 100 000 файлов**: вариант (б) в сегодняшнем формате
   для набора такого размера не проходит; нужен либо другой предел, либо двухуровневый манифест (манифест списков файлов).
   Большой манифест дорог и при чтении: проекция читает его на каждое доказательство-строку (замер рецензии: при 3125
   файлах доказательство показывается втрое медленнее).
4. Альтернатива — версия-дельта: манифест = предыдущая версия + файл изменённых строк + список удалённых ключей. Тогда
   объём версии пропорционален изменениям, но доказательство «строка есть в версии N+1» требует доказать, что строку из
   старого файла не заменили и не удалили (доказательство невхождения — упорядоченное дерево ключей), а чтение версии —
   слияние цепочки. Это другой формат доказательства и манифеста, чем сделан в цикле 10.

Что это значит для решения по D27: выбрать одно из трёх —
(а) полные версии, файлы не общие (как сейчас): просто и доказуемо, объём = число версий × размер набора; хранить
    последние N версий и те, на которые есть ссылки;
(б) мелкие файлы (по корзинам или с границами по содержимому): общие файлы без смены формата доказательства, цена —
    большой манифест и снятие предела в 100 000 файлов (двухуровневый манифест);
(в) версии-дельты с доказательством невхождения: объём минимальный, цена — новый формат и цикл работы.
Рекомендация Главного-1: (а) до появления настоящих данных и измеренной частоты изменений; (б) как первое улучшение,
если объём станет проблемой; (в) только если (б) не хватит.
