## Находки

**A. Логика**

**R-01 · P0 · D27.3, §0 п.4, §6.** «Координаты строки укладываются в `claim_evidence` без новых таблиц» — неверно. `ac.evidence_guard` (ddl_s1.sql) читает `ac.source_bytes` (bytea в базе), вырезает байтовый диапазон, сверяет sha256 и требует валидный UTF-8; форма доказательства зафиксирована (RS-02); `ac.sources.byte_length` — integer. Строка Parquet не является непрерывным UTF-8-диапазоном, байты лежат в S3, база их не читает. D26 прямо говорит обратное: доказательство проверяется по тексту в базе, оригинал лишь удостоверяет сохранность. PIPELINE-утверждению к тому же нужен узел артефакта (D17/D18). Итог: для массива «база выше заявления» превращается в заявку приложения. Изменить: описать новый вид доказательства (изменение записи Claim, валидатора, стража), кто и когда его проверяет, каноническую форму строки для хэша, манифест многофайловой версии; убрать «без новых таблиц» и «ни одно из D1–D26 не отменяется» (D2, D3, D18, D26 сужаются).

**R-02 · P0 · §0, D27.2 «одна идентичность», D27.3.** Идентичностей фактически две: `entity_id` (в пределах проекта, D4) и строка массива. Номер строки между версиями не стабилен; у баз без естественного ключа (телефонные) моста нет; параллельные ссылки дают дубли; D12 (`POSSIBLE_DUPLICATE` при COMMIT) превращает «ленивое» создание в ручную процедуру. Строка изменилась или исчезла — утверждение остаётся на старой версии без признака устаревания; старые версии надо хранить вечно (объём не посчитан). Решения о слиянии (D11) на строки массива не распространяются; «всё о лице X» по обоим профилям — соединение по ключу без индекса. Изменить: идентичность строки = (набор, объявленный первичный ключ); детерминированный ключ сущности; глобальный индекс идентификаторов (ключ → набор/версия/строка) с оценкой размера; правило поведения сущности при новой версии; политика хранения версий.

**R-03 · P1 · D27.1.** Девять типов зашиты в DDL: CHECK в `ac.entities`, слияние только внутри типа, `entity_type` неизменяем. Под какой корень идёт «Акула»? Новый корень — это DDL. «Версия схемы в каждом утверждении» (§5 п.4) меняет тело Claim и `claim_id` — это не «совместимое расширение, как Publication». Не определены: область схемы (tenant/проект), маркировка `ClassDef`, схема «на момент t» для невозвратных проекций (D16).

**R-04 · P1 · D27.1.** Миграции drop/move/cast у Foundry действуют на изменяемые правки пользователей; наши утверждения append-only (D13, D16). Буквально перенести нельзя — определить как новые утверждения либо интерпретацию при чтении, без влияния на закрытые Проверки.

**R-05 · P1 · D27.5.** D15: читатель не имеет доступа к таблицам, только проекции по допуску. Массив вводит прямой SQL-путь — не оговорено. RLS PostgreSQL привязана к таблицам PG и на Parquet-файлы/ClickHouse не распространяется (по документации pg_duckdb не проверено — README об этом молчит); масок колонок в PG16 нет. Маркировка массива — на набор: по D6 ЕГРЮЛ с руководителями целиком PERSONAL_DATA, и всё производное наследует её. Tenant: `ac.sources` — PK (tenant, source); общий ЕГРЮЛ регистрируется в каждом tenant?

**R-06 · P1 · D27.2 «внешний», D27.4.** Живые данные в проекциях ломают воспроизводимость и digest (D16); N версий набора = N источников — завышенная «поддержка факта» (D23). FDW/Multicorn исполняются внутри процесса основной базы; единая учётная запись соединения обходит ACL внешней системы. «Обратная запись» противоречит «только чтение». Изменить: федерация на отдельном узле; обратную запись вынести из D27.

**R-07 · P1 · D27.2.** 30 тысяч баз при «один класс — одна таблица» = 30 тысяч привязок «администратором»; подключение базы — физическое изменение. «Физика не меняется» верно только для Конструктора. Нужны автопрофилирование и каталог.

**R-08 · P2 · D27.1.** «Вычисляется на запросе (closure-таблица)» — closure-таблица и есть материализация.

**B. Измерение**

**R-09 · P1 · §0, §3, §5 п.1.** «9,5 секунд» — артефакт плана, не свойство раскладки. Планировщик (оценка rows=1) выбрал Nested Loop с BitmapAnd: 1123 раза пересканирован диапазон индекса из 55 000 записей. Тот же запрос с `enable_bitmapscan=off` — **23,5 мс**; с индексом `(subject, predicate)` — **20,6 мс**. Честно: ≈150× медленнее A, а не 60 000×. Убрать «секунды вместо миллисекунд».

**R-10 · P1 · §0 «диагноз ещё мягок».** Индексы несимметричны: у A три вторичных индекса, у B — `(p,v)` по всем 26 атрибутам, у C — GIN по всем ключам. Только данные: B 3,37×, C 2,17×. A с индексом на каждую колонку (78,9 МБ): B 3,46×, C 1,78×. Оценка владельца «2–3×» подтверждается, а не опровергается.

**R-11 · P1 · §3 оговорка 1, «105×», «~3 ПБ».** «Отношения почти не зависят от данных» — неверно. Мой прогон с уникальными названиями/адресами (N=20 000): B 3,87×, C 2,38×, **D 64×**, F 0,16×/0,11×. D — константа ≈55 КБ на организацию, отношение обратно пропорционально ширине строки. D — соломенное чучело: одно утверждение на запись даёт **5,66×** (296 МБ против 52 МБ). При этом D недогружена: нет строк `ac.entities`, ключей, `source_bytes`, триггеров. Переформулировать: «на 1,5–2 порядка при пополевых утверждениях; ≈6× при утверждении-записи»; убрать «150 ТБ» и «3 ПБ» (формат исходных 30 ТБ неизвестен).

**R-12 · P2 · F.** Колонки — периодические функции номера строки, ОГРН — арифметическая прогрессия; F без индексов сравнивается с A с индексами. «0,02–0,06×» из §0 убрать; плановые 0,1–0,2× мой прогон подтверждает.

Переживает критику: E ≈ A (+1–2 %); порядок A < C < B; пополевые утверждения для массивов неприемлемы; точечные запросы равны.

**C. Факты**

**R-13 · P1 · §0, §2, §3.** «5–10× к строчной СУБД на реальных справочниках» — искажено: в источнике ClickHouse 5–10× относительно несжатых данных на «typical analytical data»; PostgreSQL на той же базе 1,5–3×. «3–6 ТБ» не обосновано.

**R-14 · P2 · §2, §5 п.7.** Kitchen sink — о колонках без бизнес-смысла, не об объёме; Foundry индексирует десятки миллиардов объектов на тип, каждая строка — объект по первичному ключу, ленивого создания нет. Foundry — довод за альтернативу «объект = строка по PK», а не за D27.3. GraphDB: в таблице 43 и 159 ГБ RAM, не «сотни»; 100 байт на утверждение в 20 раз компактнее нашей D. Skinny tables создаёт поддержка Salesforce, не админ (так и в приложении).

**D. Чего не хватает**

**R-15 · P1.** Формат версий: Iceberg/Delta (манифест, снимки, эволюция схемы, построчные удаления) есть в приложении, нет в документе. Ежедневные дельты ЕГРЮЛ при «версия = полный объект» умножают объём.

**R-16 · P1.** 152-ФЗ не упомянут: телефонные базы — персональные данные; удаление строки меняет sha256 версии и рвёт все доказательства-координаты; правовое основание обработки.

**R-17 · P1.** Эксплуатация: резервное копирование и восстановление 30 ТБ; скрубер D26 перечитывает каждый объект; размер поискового индекса; pg_duckdb работает внутри процесса основной базы; рекомендуемый движок в этой среде ни разу не запускался (403) — цикл 10 в заявленном виде неисполним.

**R-18 · P2.** Не рассмотрены: секционирование PostgreSQL + BRIN; JSONB с «горячими» типизированными колонками; транзакционность и производительность соединений между профилями; стоимость переиндексации при смене привязки; утверждение-запись как промежуточный профиль.
