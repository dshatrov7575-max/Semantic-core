## Новые противоречия

**N-01 · P1 · D27.4 против D27.2/D6.** `quote` — каноническая форма *всей* строки. Утверждение об открытой колонке (статус) несёт в теле и в `claim_evidence` руководителя (PERSONAL_DATA). Маркировка по колонкам обесценивается: либо утверждение маркируется по максимуму набора, либо утечка. Изменить: хэш строки = дерево хэшей колонок; цитата = ключ + одна колонка + путь.

**N-02 · P1 · D27.4 против ONT-03/RS-02/S6R-06.** «Шлюз пишет доказательство». В ddl_s1.sql строки доказательств создаёт *только* триггер `ac.claims_after` из тела утверждения; `ac_gateway` — член `ac_storage` «и ничего больше». Буквально шлюз становится писателем утверждений. Изменить: шлюз пишет только `ac.dataset_row_checks`; доказательство по-прежнему из тела; страж требует запись проверки и берёт блокировку по ключу строки (урок S6R-01/04). `span_start/span_end NOT NULL` — таблицу придётся менять; сказать прямо.

**N-03 · P1 · D27.3 против D4/D12.** (а) «D12 остаётся для прочих путей» — неверно: по коду `ac.soft_keys_check` отвергает при COMMIT любое совпадение скелетов без решения `DISTINCT` или различающихся квалификаторов WEAK-ключей (`ac.separated`); разные ИНН там не разделяют. Одноимённых ООО в ЕГРЮЛ тысячи — ленивая и тем более «целиком» материализация упрутся в стража; нужно правило разделения по разным сильным идентификаторам. (б) Детерминированный id от *одного* идентификатора: строка с ОГРН и строка с ИНН дают две сущности; уже заведённая аналитиком сущность с этим ИНН — конфликт `entity_keys_one_owner`. Правило: сначала поиск владельца ключа, создание — если его нет; порядок типов идентификаторов. (в) Телефон сильным идентификатором лица быть не может. Сам формат совместим: `ent_` + 64 hex проходит `^ent_[a-z0-9_]{2,64}$`.

**N-04 · P1 · D27.1 против D7/D18.** «Новые утверждения с теми же доказательствами»: индекс `claim_evidence_one_node` (ddl_s4.sql) — один узел графа подпирает одно доказательство; PIPELINE-утверждению нужен свой receipt и артефакт (D7, D19); у HUMAN-утверждений конвейер меняет авторство. Изменить: миграция = новый артефакт, либо cast только при чтении.

**N-05 · P1 · D27.3 против D27.6.** «Поиск внутри неиндексируемого набора — его собственными средствами», но читатель не имеет доступа ни к таблицам, ни к файлам. Без функции поиска через шлюз (с фильтром по маркировкам колонок) неиндексированные базы пользователю недоступны.

**N-06 · P2 · скрипт, D2.** `CREATE TABLE claims_rec (LIKE claims INCLUDING ALL)` унаследовал индекс `(predicate, literal->>'value')` — btree по тексту всей строки (у меня 8,2 из 13,9 МБ индексов) — и дубль `(subject, predicate)`. Без них D2 «с индексами» ≈7,8× (мой расчёт на N=5000), а не 10,7–11,4×. Исправить скрипт; «≈7–11×» → «≈7–8×».

**N-07 · P2 · §0, §5 п. 1.** «60–100×» не совпадает с .out: там 81,18–107,61× (60 — из моего варианта с более широкими строками; так и написать). «≈55 КБ» — в .out 56,4–56,6 КБ. «На два порядка медленнее на аналитике» — по .out 59–72×; в §3 верно «в десятки раз».

**N-08 · P2 · D27.3 «целиком».** Нет порога: по таблице автора ≈6 КБ на строку — ЕГРЮЛ ≈45 ГБ, телефонная база на 100 млн ≈0,6 ТБ.

«Поддержка по семейству» D23 не противоречит: тот же приём, что D21.
