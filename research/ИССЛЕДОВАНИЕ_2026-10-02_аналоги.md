## Сводка 1. Palantir Foundry и Gotham: онтология над физическим хранением

Примечание: часть страниц palantir.com отдавалась неполно; такие места помечены.

1. Foundry Ontology
- Соответствие: object type = датасет, объект = строка, свойство = колонка [palantir.com/docs/foundry/ontology/core-concepts]. Тип создаётся из backing datasource: колонки автоматически мапятся в свойства (можно отбросить), обязательны primary key (уникален по строкам) и title key; MapType/StructType в backing-датасете запрещены [palantir.com/docs/foundry/object-link-types/create-object-type]. Тип без датасета возможен: объекты создаются только Actions [palantir.com/docs/foundry/object-link-types/object-types-overview].
- Связи: 1:1 и 1:N через foreign key; M:N через join-table датасет; object-backed link через промежуточный тип с метаданными [palantir.com/docs/foundry/object-link-types/create-link-type]. Связь двусторонняя, не пересекает границы Ontology [palantir.com/docs/foundry/object-link-types/link-types-overview].
- Интерфейсы: абстрактная «форма» типа; тип реализует несколько интерфейсов; интерфейсы наследуются, в т.ч. от нескольких; поддержка в платформе неравномерная [palantir.com/docs/foundry/interfaces/interface-overview]. Наследование object type от object type в найденной документации не описано.
- Изменения: Ontology Manager; proposals «как pull request», по задаче на каждую изменённую сущность, ревью, merge; автоматического отката proposal нет; механизм уходит в Global Branching [palantir.com/docs/foundry/ontologies/ontology-branches-legacy]. В Global Branching ветка включает схему датасета и определение object type [palantir.com/docs/foundry/foundry-branching/overview].
- Миграции ✔: смена типа свойства, смена ID или удаление свойства с правками, смена входного datasource блокируют сохранение до выбора: Drop edits / Move edits / Cast to new type (до 500 за раз); смена display name, title key, render hints миграции не требует; есть Revert migration [palantir.com/docs/foundry/object-edits/schema-migrations]. При смене схемы создаётся replacement-pipeline в фоне без остановки обслуживания; полная переиндексация [palantir.com/docs/foundry/object-indexing/funnel-batch-pipelines].

2. Object Storage V1 и V2
- V1 (Phonograph) совмещал индексацию, хранение, запросы и историю правок; V1 недоступен после 30.06.2026 [palantir.com/docs/foundry/object-backend/overview; palantir.com/docs/foundry/object-databases/object-storage-v1].
- V2 ✔: сервис Funnel «читает данные из datasources Foundry (датасеты, restricted views, потоковые источники) и правки пользователей (из Actions) и индексирует их в object databases»; object databases — «сервисы, хранящие проиндексированные данные объектов… для быстрых запросов» [palantir.com/docs/foundry/object-backend/overview]. Слова «копия» и явного «источника истины» в документации нет [palantir.com/docs/foundry/object-indexing/overview].
- Правки: только через Actions; сразу применяются к индексу, периодически сбрасываются в датасеты, управляемые Funnel; слияние по primary key; конфликт: «правки пользователя всегда выигрывают» (по умолчанию) или «самое свежее значение» [palantir.com/docs/foundry/object-edits/how-edits-applied; palantir.com/docs/foundry/object-indexing/funnel-batch-pipelines]. Materializations: датасеты «последнего состояния» (источник + правки) [palantir.com/docs/foundry/object-edits/materializations].
- Индексация инкрементальная; полная, если изменилось >80% строк [palantir.com/docs/foundry/object-indexing/funnel-batch-pipelines].

3. Масштаб ✔
- V2: индексация «порядка десятков миллиардов объектов на один тип»; до 2000 свойств на тип; до 10 000 объектов в одном Action [palantir.com/docs/foundry/object-backend/overview].
- Антипаттерн Kitchen Sink: лишние технические колонки раздувают индекс; свойства нужно курировать [palantir.com/docs/foundry/ontology/ontology-anti-patterns].
- Для очень больших таблиц вне Ontology — Contour; объектные агрегации в Quiver до 50 000 строк [palantir.com/docs/foundry/analytics/types-of-analysis]. Derived properties свободны до ~10k объектов [palantir.com/docs/foundry/ontology/ontology-structural-guidance].

4. Интеграция
- Data Connection: 200+ коннекторов (БД, S3/Azure/GCP, REST/GraphQL/OData, Kafka/Kinesis, SAP/Salesforce); batch, streaming, CDC, файловые синхронизации = копирование в Foundry; агенты у клиента; экспорт, webhooks [palantir.com/docs/foundry/data-connection/overview].
- Query-in-place: virtual tables читают и пишут таблицы внешних платформ без хранения данных в Foundry [palantir.com/docs/foundry/transforms-python/tables-overview]; compute pushdown для BigQuery, Databricks, Snowflake [palantir.com/docs/foundry/transforms-python/tables-compute-pushdown]. Virtual table может быть backing datasource объектного типа (Snowflake) [community.palantir.com/t/6509].
- Webhooks в Actions: writeback (до изменений, при сбое ничего не меняется) и side effect (после, best effort) [palantir.com/docs/foundry/action-types/webhooks].
- OSDK: генерируется из метаданных Ontology; TypeScript, Python, Java, OpenAPI [palantir.com/docs/foundry/ontology-sdk/overview].

5. Gotham
- Патент: онтология = типы объектов и свойств (с компонентами) и парсеры; «онтология БД обычно фиксирована, пользователь меняет её в любой момент» [patents.google.com/patent/US7962495B2/en]. Gotham API: RevDB «на основе динамической онтологии» [palantir.com/docs/gotham/api; palantir.com/docs/gotham/api/revdb-resources/objects/object-basics].
- Хранилище: Postgres или Oracle; «каждый элемент данных привязан к источнику, ограничения доступа можно задавать на уровне отдельных атрибутов»; ACL ownership/write/read/discovery; история изменений объекта [assets.applytosupply.digitalmarketplace.service.gov.uk/g-cloud-14/documents/92736/801146272055049-service-definition-document-2024-11-26-1253.pdf]. У свойства в API: propertyId, propertyType, value, security (portion markings, permissions) [palantir.com/docs/gotham/api/revdb-resources/objects/add-object-property]. Патент ревизионной БД: новая строка на каждое изменение, realm-колонки [patents.google.com/patent/US8930331B2/en].
- Federated sources: query-in-place, объект читается как нативный, но только чтение [palantir.com/docs/gotham/api/revdb-resources/federated-sources/federated-source-basics].

6. Доступ
- Права на схему (типы) отделены от прав на данные (объекты) [palantir.com/docs/foundry/object-permissioning/overview].
- Object security policy по умолчанию наследует markings, организации и классификации backing datasource; property policies дают column-level, вместе с object policies — cell-level; без доступа значение null; primary key защитить нельзя; защита только при чтении [palantir.com/docs/foundry/object-permissioning/object-security-policies].
- Restricted view: row-level по правилам из атрибутов пользователя, колонок и значений; служит backing datasource типа [palantir.com/docs/foundry/security/restricted-views].

Главные уроки для нашей архитектуры (по сводке 1)
1. Логическая модель (типы, свойства, связи, интерфейсы) хранится как метаданные с маппингом на физические колонки; её изменение — перенастройка маппинга и фоновая переиндексация, а не миграция данных.
2. Объектный слой — индекс над данными плюс отдельный слой правок, сливаемый по ключу с явной стратегией конфликта.
3. Не всё становится объектами: огромные таблицы остаются датасетами или виртуальными; объектами идут курируемые выборки с отобранными колонками.
4. Внешние БД подключаются двумя режимами — копия и query-in-place; у каждого свои гарантии по правам и правкам (federated только чтение).
5. Изменения схемы при наличии правок требуют явной миграции (drop/move/cast) и ревью; права и происхождение задаются на уровне источника и свойства.

## Сводка 2. Класс SemanticWiki и семантические СУБД

1. Semantic MediaWiki
- smw_object_ids выдаёт целочисленный smw_id всем страницам, свойствам и подобъектам. Все прочие таблицы ссылаются на неё [https://mintlify.wiki/SemanticMediaWiki/SemanticMediaWiki/architecture/database-schema].
- Значения лежат в таблицах по ТИПУ данных: smw_di_number, _blob, _bool, _uri, _time, _coords, _wikipage, _container. Строка имеет вид (s_id, p_id, o_*) [https://www.semantic-mediawiki.org/wiki/Help:Database_schema]. Новое свойство попадает в таблицу своего типа, DDL не нужен.
- Fixed property tables (smw_fpt_*) без p_id, свойство неявное. Включаются через $smwgFixedProperties и setupStore.php; для существующих свойств нужен rebuildData.php. Рекомендация: от 1000, лучше от 25 000 значений [https://www.semantic-mediawiki.org/wiki/Help:Fixed_properties]. То есть выдвижение горячего свойства в отдельную таблицу делает админ, это DDL.
- Свойство определяется страницей в пространстве Property, тип задаётся как [[Has type::Number]] [https://www.semantic-mediawiki.org/wiki/Help:Special_property_Has_type]. Подсвойство: [[Subproperty of::Parent]] [https://www.semantic-mediawiki.org/wiki/Help:Special_property_Subproperty_of]. Глубина по подкатегориям по умолчанию 10 [https://www.semantic-mediawiki.org/wiki/Help:$smwgQSubcategoryDepth]. Наследование атрибутов от класса в проверенных страницах не описано.
- ElasticStore реплицирует данные в Elasticsearch и отвечает на #ask; SQL остаётся обязательным хранилищем [https://www.semantic-mediawiki.org/wiki/Help:ElasticStore]. SPARQLStore — альтернативный бэкенд запросов, не замена SQLStore [https://www.semantic-mediawiki.org/wiki/Help:SPARQLStore].
- Пределы: «миллионы строк», ограничитель — сложные запросы [https://www.semantic-mediawiki.org/wiki/FAQ]. Issue #6559: в smw_di_blob много дублей, нормализация даёт экономию 24–87% [https://github.com/SemanticMediaWiki/SemanticMediaWiki/issues/6559].

2. Wikibase / Wikidata
- Сущность хранится как JSON в содержимом страницы MediaWiki [https://doc.wikimedia.org/Wikibase/master/php/docs_storage_entities.html]. Термы нормализованы (wbt_*), обновляются отложенно [https://doc.wikimedia.org/Wikibase/master/php/docs_storage_terms.html].
- Цена денормализации: старая wb_terms — 900 ГБ (2018) → 946 ГБ (2019), более 70% дублирования, семь индексов около 590 ГБ; заменена нормализованной схемой [https://phabricator.wikimedia.org/T221764].
- Индекс запросов отдельный: WDQS на Blazegraph; полнотекстовый поиск — Elasticsearch [https://en.wikipedia.org/wiki/Wikidata; https://en.wikipedia.org/wiki/Wikibase].
- Масштаб: около 116 млн элементов и около 16 млрд триплетов. Blazegraph не распределённый и снят с поддержки [https://www.hpcwire.com/bigdatawire/2025/07/10/scaling-the-knowledge-graph-behind-wikipedia/]. Граф разделён на основной (~77 млн элементов, 8,4 млрд триплетов) и научный (~45 млн, 8,7 млрд) [https://ceur-ws.org/Vol-4064/PD-paper3.pdf]. Известные боли: таймауты WDQS, лаг обновления [https://www.wikidata.org/wiki/Wikidata:WikiProject_Limits_of_Wikidata].

3. XWiki
- Класс — страница; объект — экземпляр класса, привязанный к странице [https://www.xwiki.org/xwiki/bin/view/documentation/xs/dev/data-model/x-classes/; …/x-objects/].
- Таблицы: xwikidoc, xwikiobjects, xwikiproperties; значения в таблицах по типу: xwikistrings, xwikiintegers, xwikilongs, xwikifloats, xwikidoubles, xwikidates, xwikilargestrings, xwikilists [https://www.xwiki.org/xwiki/bin/view/Documentation/DevGuide/DatabaseSchema/]. Две строки на каждое значение.
- Custom mapping выносит класс в собственную таблицу «для производительности при многих экземплярах» — через hbm.xml, то есть DDL [https://www.xwiki.org/xwiki/bin/view/Documentation/DevGuide/Tutorials/CustomMapping/].

4. TypeDB
- Три корневых вида типов: entity, relation, attribute, плюс подтипизация и наследование [https://typedb.com/docs/]. В 3.x каждый подтип владеет всеми атрибутами и играет все роли надтипов [https://typedb.com/docs/reference/typedb-2-vs-3/diff/].
- Схема меняется командами define/redefine/undefine [https://typedb.com/fundamentals/schema-and-data-migration-3-0/]. Schema-транзакция эксклюзивна против других schema и write-транзакций [https://typedb.com/docs/core-concepts/typedb/transactions/]. Хранилище RocksDB, 3.0 переписана на Rust [https://github.com/typedb/typedb].

5. OBDA / виртуальные графы ✔
- Ontop публикует произвольную реляционную БД как граф знаний без копирования данных: SPARQL переписывается в SQL по R2RML-маппингам и онтологии; PostgreSQL, MySQL, Oracle, SQL Server, DB2, Snowflake, BigQuery, DuckDB и федераторы Denodo/Dremio/Trino; Apache 2.0 [https://ontop-vkg.org/guide/].
- R2RML — рекомендация W3C от 27.09.2012; логическая таблица может быть SQL-view без изменения БД [https://www.w3.org/TR/r2rml/].
- Stardog virtual graphs: маппинги SMS/R2RML, переписывание SPARQL в SQL на лету, при необходимости материализация [https://docs.stardog.com/virtual-graphs/].

6. Salesforce Force.com
- Данные всех тенантов — в одной таблице MT_Data с колонками Value0…Value500 (универсальный текст, приведение через TO_NUMBER/TO_DATE) [https://tool.lu/deck/kM/detail; https://cirra.ai/articles/salesforce-database-architecture-explained]. Метаданные: MT_Objects и MT_Fields; реальные таблицы не создаются [https://developer.salesforce.com/ja/wiki/multi_tenant_architecture].
- Цена универсальности: на flex-колонках нельзя строить нативные индексы, поэтому значения синхронно копируются в pivot-таблицу Indexes с типизированными колонками; также UniqueFields, Relationships, Clobs, FallbackIndex, NameDenorm [https://www.oreilly.com/library/view/the-forcecom-multitenant/30000LTI00089/30000LTI00089_ch08lev1sec5.html].
- Skinny tables: до 200 колонок, создаются только через поддержку Salesforce [https://developer.salesforce.com/docs/atlas.en-us.salesforce_large_data_volumes_bp.meta/salesforce_large_data_volumes_bp/ldv_deployments_infrastructure_skinny_tables.htm].

7. RDF-хранилища ✔
- Jena TDB: словарь node table, NodeId 8 байт, три индекса SPO/POS/OSP [https://jena.apache.org/documentation/tdb/architecture.html]. Oxigraph: RocksDB, id2str и девять индексов [https://github.com/oxigraph/oxigraph/wiki/Architecture]. Virtuoso: RDF_QUAD(G,S,P,O), колоночное хранение ≈1/3 строчного [https://docs.openlinksw.com/virtuoso/rdfperfrdfscheme/].
- GraphDB, таблица сайзинга: 1,5 млрд утверждений → 150 ГБ образа и 43 ГБ RAM; 30 млрд → 2900 ГБ и 159 ГБ RAM (≈100 байт на утверждение) [https://graphdb.ontotext.com/documentation/10.7/requirements.html].

Общие приёмы, которые повторяются у всех
1. Схема как данные: классы и свойства лежат в метаданных или на страницах (SMW Property:, xwikiclasses, MT_Fields, property-сущности Wikibase).
2. Типизированный EAV: значение в таблице по типу данных (smw_di_*, xwiki*) или в типизированной pivot-таблице (Indexes у Salesforce) плюс реестр ID.
3. Продвижение горячих свойств в отдельные структуры (fixed tables, custom mapping, skinny tables), но это действие админа и DDL.
4. Отдельный поисковый или запросный индекс (Elasticsearch, Blazegraph, FallbackIndex), SQL остаётся источником истины.
5. Словарное кодирование и нормализация против дублей (wbt_*, id2str, smw_object_ids): wb_terms имел более 70% дублей, SMW-blob 24–87%.
6. Иерархия считается на запросе с ограничением глубины (SMW 10 уровней, T-mappings Ontop, подтипы TypeDB) и не материализуется в схеме.

## Сводка 3. Виртуализация данных и массовое хранение

Оговорка: сайты ФНС (nalog.gov.ru, ftp.egrul.nalog.ru) недоступны из среды (403), поэтому п.7 по вторичным источникам. «Вендор» = заявление поставщика.

1. FDW
- postgres_fdw (ядро PG16): WHERE уходит на удалённый сервер только для встроенных IMMUTABLE-функций; join foreign-таблиц одного сервера отправляется целиком; async_capable; IMPORT FOREIGN SCHEMA [https://www.postgresql.org/docs/16/postgres-fdw.html; https://www.postgresql.org/docs/16/sql-importforeignschema.html].
- oracle_fdw 2.9.0 (06.2024), pushdown WHERE/ORDER BY/join, IMPORT, DML [https://github.com/laurenz/oracle_fdw]. mysql_fdw REL-2_9_3, PG13–18 [https://github.com/EnterpriseDB/mysql_fdw/releases]. tds_fdw 2.0.5 (MSSQL/Sybase), PG16/17, pushdown WHERE, IMPORT, без join-pushdown и записи [https://github.com/tds-fdw/tds_fdw]. odbc_fdw (pgspider) [https://github.com/pgspider/odbc_fdw]. jdbc_fdw (pgspider) PG13–17 [https://github.com/pgspider/jdbc_fdw]. Multicorn2 (Python-FDW) PG14–18 [https://github.com/pgsql-io/multicorn2].
- parquet_fdw — только чтение, experimental [https://github.com/adjust/parquet_fdw]; parquet_s3_fdw PG13–17, S3/MinIO [https://github.com/pgspider/parquet_s3_fdw]; clickhouse_fdw архивирован 29.12.2025 → преемник pg_clickhouse (ClickHouse, PG14+) [https://github.com/ildus/clickhouse_fdw; https://github.com/ClickHouse/pg_clickhouse]; duckdb_fdw 2.0.1 (PG13–18) [https://github.com/alitrack/duckdb_fdw]; pg_duckdb 1.1.1 (PG14–18) [https://github.com/duckdb/pg_duckdb]. Большинство FDW не поддерживаются PGDG [https://wiki.postgresql.org/wiki/Foreign_data_wrappers].

2. ClickHouse
- ClickBench, 100M строк: 9,26 GiB против ~100 GiB в PostgreSQL (≈10×, вендор); строчные СУБД 1,5–3×, колоночные 5–10×, low-cardinality 30×+ [https://clickhouse.com/resources/engineering/database-compression]. Stack Overflow датасет: 2,86× в целом [https://clickhouse.com/docs/data-compression/compression-in-clickhouse]. NOAA: 131,58 GiB → 4,07 GiB (32:1) [https://clickhouse.com/blog/optimize-clickhouse-codecs-compression-schema].
- Движки/функции: ODBC, JDBC, MySQL, PostgreSQL, MongoDB, S3, Kafka, URL, iceberg, deltaLake [https://clickhouse.com/docs/engines/table-engines; https://clickhouse.com/docs/sql-reference/table-functions]. `postgresql()`: на PG уходят только простые WHERE [https://clickhouse.com/docs/sql-reference/table-functions/postgresql]. Dictionaries: ODBC, MySQL, PostgreSQL, HTTP, файл [https://clickhouse.com/docs/sql-reference/dictionaries].

3. Колоночные файлы
- DuckDB read_parquet: filter/projection pushdown, S3/HTTP range-чтение [https://duckdb.org/docs/current/data/parquet/overview.html; https://duckdb.org/docs/current/core_extensions/httpfs/s3api.html]; расширение postgres: ATTACH, pushdown, запись [https://duckdb.org/docs/current/core_extensions/postgres/overview.html]. Iceberg — слой метаданных над Parquet, snapshot isolation, эволюция схемы [https://iceberg.apache.org/docs/latest/].
- Parquet против CSV: 11,2M строк × 20 колонок — CSV 1,09 GB, Parquet/ZSTD 164 MB (6,8×), Snappy 218 MB (5,1×) (вендор MotherDuck) [https://motherduck.com/learn/csv-vs-parquet-benchmark/].

4. Накладные расходы PostgreSQL
- Страница 8 kB, заголовок 24 B, 4 B на item pointer, заголовок кортежа 23 B + null bitmap, выравнивание MAXALIGN [https://www.postgresql.org/docs/16/storage-page-layout.html]. EAV: каждое значение — строка с собственным заголовком; бенчмарк блога (10M × 7 свойств): EAV 171 MB против JSONB 78 MB [https://www.razsamuel.com/postgresql-jsonb-vs-eav-dynamic-data/]. JSONB: GIN jsonb_path_ops меньше jsonb_ops; документация рекомендует фиксированную структуру [https://www.postgresql.org/docs/16/datatype-json.html]. TOAST сжимает только значения > ~2 kB [https://www.postgresql.org/docs/16/storage-toast.html]. B-tree дедупликация (PG13+) [https://www.postgresql.org/docs/16/btree-implementation.html].
- Колоночные варианты для PG16: Citus columnar (zstd, append-only, без UPDATE/DELETE) [https://docs.citusdata.com/en/stable/admin_guide/table_management.html]; Hydra (AGPL) [https://github.com/hydradatabase/hydra]; pg_analytics архивирован [https://github.com/paradedb/pg_analytics]; TimescaleDB «90–97%» на time-series (вендор, Timescale License) [https://www.tigerdata.com/learn/postgresql-compression].

- Открытые данные ФНС: XML в ZIP по датам, полный снимок на начало года, затем ежедневные дельты; до 1000 записей в файле (2018) [https://habr.com/ru/companies/hflabs/articles/413891/; https://habr.com/ru/post/496900/]. Полный снимок ≈15 ГБ ZIP (сторонний README) [https://github.com/atomno-mcp/mcp-egrul].
- Ключи: ОГРН не меняется до исключения из реестра; при реорганизации — новый [https://office.ru/faq/menyaetsya-li-ogrn-pri-smene-naimenovaniya/]. ОГРНИП при повторной регистрации ИП новый [https://e-kontur.ru/enquiry/1751/chto-takoe-ogrnip].

Что из этого напрямую применимо к PostgreSQL-16-ядру
1. Живые БД без копирования: postgres_fdw, oracle_fdw, mysql_fdw, tds_fdw, odbc/jdbc_fdw с IMPORT FOREIGN SCHEMA; REST и SDK через Multicorn2. Join между разными серверами и сложные агрегаты выполняются локально.
2. Сотни ГБ–ТБ справочников: вместо heap хранить Parquet/ZSTD и читать через pg_duckdb, parquet_s3_fdw или duckdb_fdw (все с поддержкой PG16). Альтернатива — ClickHouse с pg_clickhouse или по протоколу PostgreSQL.
3. Утверждения с провенансом: не копировать значения в EAV (≥27 B на строку плюс повтор ID); хранить ссылку (источник, ключ, поле) и материализовать только сами утверждения.
4. Живые системы: Debezium для PG/MySQL/SQL Server/Oracle/MongoDB; Kafka Connect JDBC только опрашивает и не видит DELETE. Для «не копировать» — FDW или Trino/Denodo/Teiid.
5. ЕГРЮЛ/ЕГРИП: XML-снимок плюс ежедневные дельты, ОГРН/ОГРНИП — стабильные ключи (ОГРНИП меняется при повторной регистрации ИП, ИНН физлица сохраняется).
