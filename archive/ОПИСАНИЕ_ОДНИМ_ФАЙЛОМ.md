просьбе владельца, чтобы работу **посмотрели и раскритиковали другие нейросети**.

## Что это

Общее ядро данных для шести продуктов одного владельца (извлечение смысла из технических документов, анализ
конфликтов, мониторинг СМИ, досье, проверки контрагентов, базы знаний). Ядро построено языковой моделью за четыре дня
(30.09–03.10.2026) в одиннадцать циклов; результат каждого цикла отдавался на независимую рецензию другому экземпляру той же модели
(с отклонениями, названными в `02_МЕТОДИКА.md` §6).
Здесь — описание того, что получилось, как это делалось, вся история рецензий и весь код.

## Что от вас нужно

Критика. Не оценка «хорошо / плохо», а: что неверно, что упущено, что сделано лишнего, что сломается первым, что вы
сделали бы иначе и почему. Автор перечислил собственные сомнения и 15 прямых вопросов в
`05_СЛАБЫЕ_МЕСТА_И_ВОПРОСЫ.md` — но самое ценное то, чего в этом списке нет.

Просьбы к критику:
1. Отделяйте «это ошибка» (с примером входа или сценария) от «я бы сделал иначе».
2. Не верьте числам и заявлениям автора на слово: код и выводы прогонов приложены.
3. Если вы прочитали только часть архива — скажите, какую.

# 01. Платформа: что построено

Состояние на 03.10.2026 (контрольная точка после цикла 11). Всё, что здесь названо «исполнено», существует как код в
каталоге `код/` этого архива и проверено прогонами (числа — §13). Всё, чего нет, перечислено в §14 и в файле
`05_СЛАБЫЕ_МЕСТА_И_ВОПРОСЫ.md`.

## 1. Назначение

Владелец строит семейство из шести продуктов и хочет, чтобы они стояли на одном ядре данных (рабочее имя — TechSense
Common Platform; проект называется «Архитектура семантики»; ориентир владельца — «аналог платформы Palantir»):

| Продукт | Что делает | Что ему нужно от ядра |
|---|---|---|
| **TechSense** | извлекает смысл из технических документов (UD → UP → PropBank → AMR/UMR, смысловой граф), отвечает с провенансом до фрагмента | принять граф разбора как подписанный артефакт и превратить его в проверяемые утверждения об оборудовании |
| **Конфликтология** | анализ конфликтов: стороны, события, субъекты влияния, явные и неявные связи | конфликты, события, лица, организации и связи как утверждения с доказательствами |
| **Web Monitoring** | сбор СМИ и соцсетей | источник = байты одного забора; одна статья, полученная много раз, — одна публикация |
| **Dossier Analyser** | досье на физлиц, юрлиц, имущество; база знаний по конкурентам | **одна сущность в проекте — строго один раз**; расхождения источников видны, а не теряются |
| **Compliance Check** | проверки партнёров и заёмщиков | **«Проверка» — самостоятельный объект**; одно лицо проверяется много раз в разных профилях; «не выявлено» должно быть доказуемо |
| **SemanticWiki** | базы знаний на произвольную тему | пользователь сам вводит классы, атрибуты и связи, не меняя физическую базу |

Ядро — это **общий язык данных** этих продуктов: модель записей, правила, проверяющая программа и база данных, которая
держит те же правила сама. Интерфейсов, сборщиков данных и поиска в ядре нет.

## 2. Принципы (на них держится всё остальное)

1. **Утверждение отдельно от сущности (D2).** Сущность хранит только идентичность. Всё, что о ней известно, —
   утверждения (claims) с доказательством до байтового фрагмента источника или до строки набора данных. Досье, отчёт
   Проверки, страница вики, карточка оборудования — проекции одних и тех же утверждений.
2. **Адресация по содержимому (D3).** Источник — `src:sha256:<байты>`; утверждение и квитанция (receipt) —
   sha256 от канонической формы JSON (RFC 8785 JCS, UTF-8) записи без собственного идентификатора. Профиль чисел
   целочисленный (деньги в копейках, величины десятичной строкой) — без чисел с плавающей точкой.
3. **Неизменяемость.** Записи только добавляются. Меняются лишь статус сущности (один переход из ACTIVE) и статус/итог
   Проверки. Мнение об утверждении — отдельная запись-рецензия, а не правка.
4. **Fail-closed (D9).** Любая непредвиденная ошибка проверки — отказ, а не «прошло». Квитанция без ключа в реестре
   доверия и доказательство без байтов источника отвергаются (источник, на который никто не ссылается, может быть без
   байтов; набор без квитанций проходит и без реестра доверия).
5. **«База выше заявления».** База не верит приложению: ключи идентичности вычисляет сама, время ставит сама,
   доказательство сверяет с байтами сама, производные строки порождает только триггером из тела записи.
6. **Производное не шире входов (D6).** Маркировка утверждения не слабее маркировки каждого источника, субъекта и
   объекта; маркировка Проверки — не слабее субъекта и каждого её утверждения.
7. **Невозвратность ответов (D16).** Ответ проекции на прошедший момент времени не должен меняться позже. Закрытая
   Проверка читается на момент закрытия. Известные исключения — в §12.
8. **Правило — только с вектором и мутантом.** Правило, которое не проверяется кодом и не имеет негативного примера,
   правилом не считается (подробно — `02_МЕТОДИКА.md`).

## 4. Модель записей

Область видимости: **tenant** (организация-владелец данных) → **project** (один из шести продуктов; граница ссылок и
доступа). Источники общие для tenant, сущности и утверждения принадлежат проекту.

| Запись | Идентичность | Суть | Главные правила |
|---|---|---|---|
| `Project` | `prj_…` | tenant, продукт, маркировка по умолчанию | граница ссылок |
| `Source` | `src:sha256:<байты>` | вид (документ, статья, пост, выписка, результат поиска в реестре, страница, заметка аналитика, **версия набора данных**), наблюдения (`observations[]`: когда, откуда, кем; необязательная ссылка на сырой оригинал) | хэш сверяется всегда; повторный забор — новое наблюдение, а не новый источник |
| `Entity` | `ent_…` | проект, один из 10 типов, `identity` по типу, статус (ACTIVE / MERGED / RETIRED) | контрольные цифры идентификаторов; достаточность идентичности; уникальность в проекте; корректность слияния |
| `Claim` | `clm:sha256:<JCS>` | субъект, предикат, объект (сущность или литерал), уточнения, срок действия, доказательства, кто произвёл (человек или конвейер), время записи, маркировка | область и диапазон предиката; доказательство подтверждается байтами; маркировка не шире входов |
| `ClaimReview` | `rev_…` | статус утверждения: ACCEPTED / DISPUTED / REFUTED / WITHDRAWN; кто, заявленное и системное время | порядок — по системному времени; задним числом под закрытую Проверку нельзя |
| `Check` | `chk_…` | субъект, профиль, дата «на которую», статус, итоги по измерениям (результат, риск, утверждения, следы поиска), общий риск | см. §7 |
| `ArtifactReceipt` | `rcp:sha256:<JCS>` | производитель, запуск, адрес артефакта, входы, выпущенные утверждения, подпись Ed25519 | ключ — только из реестра доверия tenant; одно PIPELINE-утверждение — ровно в одной квитанции |
| `IdentityDecision` | `idd_…` | решение аналитика: DISTINCT («это разные») или QUALIFY (однократно уточнить слабый ключ) | §5 |
| `Publication` | `pub:sha256:<JCS>` | статья издания над заборами-источниками | §9 |
| `ClassDef`, `LinkDef`, `IdentifierDef` | `(tenant, id, версия)` | схема tenant как данные | §10 |
| `trust_anchors` (вне набора) | `key_…` | ключи служб: tenant, служба, интервал действия, отзыв | ошибка реестра — не доверяем ни одному ключу этого tenant |

## 5. Идентичность: «одна сущность в проекте — один раз» (D4, D11, D12)

Сущность получает набор ключей, который **вычисляет база** из `identity` (SQL-порт тех же функций, что в валидаторе;
о проверке совпадения — §13):

- **сильные ключи**: ИНН, ОГРН, ОГРНИП, ИНН+КПП филиала, кадастровый номер, VIN, IMO, регистрационные номера. Один ключ — один владелец в проекте;
- **слабые ключи**: ФИО + дата рождения; событие (название + дата [+ место]); понятие. Совпадение — дубль, если обе
  стороны не несут различающий уточнитель;
- **точный ключ** строки: NFC, удаление невидимых символов, свёртка ширины, casefold, тире → «-», без кавычек,
  схлопнутые пробелы. **Скелет**: плюс NFKC, двойники латиницы/греческого/армянского/чероки → кириллица, ё → е, снятие
  ударений. Совпадение скелетов у людей и организаций — ошибка; у тегов оборудования и понятий — «возможный дубль»,
  который база отвергает при фиксации, пока аналитик не записал решение `DISTINCT`;
- **слияние**: MERGED → в ACTIVE сущность того же типа и проекта; ключи переходят выжившей; цепочки запрещены;
  маркировка выжившей не может быть строже маркировки сливаемой (иначе имя закрытой сущности стало бы видно читателям
  открытой); пару, признанную различной, слить нельзя;
- **версия Юникода закреплена (14.0.0, D25)**: таблицы базы сгенерированы из валидатора; строка с символом, не
  назначенным в этой версии, в identity отвергается (PostgreSQL нормализует по более новой версии — урок цикла 11).

Межпроектной идентичности нет: одна компания в четырёх проектах — четыре сущности (открытый вопрос O1 с версии v0.1).

## 6. Утверждение и три формы доказательства

1. **Цитата (`SPAN`)** — источник, байтовый диапазон, sha256 цитаты. Диапазон не режет символ UTF-8; при чтении
   цитата перечитывается из байтов (`verified`).
2. **Узел графа** (для утверждений конвейера, D17–D18) — доказательство опирается на узел-отношение сохранённого
   артефакта разбора; фрагмент лежит внутри якоря узла; предикат — по роли узла; субъект и объект — сущности с
   ключами узла; литерал — из узла.
3. **Строка набора данных (`ROW`, цикл 10)** — §11.

Кто произвёл: `HUMAN` (аналитик) или `PIPELINE` (служба; тогда обязательна квитанция). Статус утверждения на момент
t — последний по системному времени статус рецензии; без рецензий — `ASSERTED`.

Противоречие источников по однозначному предикату — **предупреждение**, а не ошибка (D10): хранятся обе версии,
проекция пишет одно предложение с пояснением расхождения.

## 7. Проверка (Compliance, D5)

Профили: `EXPRESS_NEGATIVE`, `TENDERS_ONLY`, `SOCIAL_ONLY`, `FULL` (шесть измерений: негатив, тендеры, соцсети,
корпоративные связи, имущество, суды). Правила:

- по одному лицу — сколько угодно Проверок; цепочка `previous_check_id` (тот же субъект с учётом слияний, предыдущая
  завершена до запроса новой);
- у завершённой Проверки каждое измерение профиля имеет итог; `FOUND` ⇔ есть утверждения; `NOT_FOUND` ⇒ риск NONE;
  общий риск = максимум;
- **«не выявлено» подтверждается следом поиска**: у каждого измерения — запись «где, что, когда, кем искали» в окне
  [запрос; завершение]. Источник с результатом поиска к следу приложить можно, но **не обязательно**: без него след —
  заявление проверяющего, а не доказательство (в эталонном мире источник приложен к одному поиску);
- утверждение входит в Проверку, только если оно о субъекте (или его слитом дубле), относится к измерению и имело
  статус ACCEPTED **на момент завершения по системному времени**;
- строки закрытой Проверки принимаются только в транзакции, которая её закрыла; история запечатывается (D13);
- субъект открытой Проверки нельзя слить или вывести из употребления (цикл 11).

## 8. Доступ (D6, D15, D24)

Маркировка = уровень (`PUBLIC` < `INTERNAL` < `CONFIDENTIAL` < `RESTRICTED`) + категории (`PERSONAL_DATA`,
`COMMERCIAL_SECRET`, `OFFICIAL_USE`). У физлица категория персональных данных обязательна.

Читатель (`ac_reader`) **не имеет доступа ни к одной таблице** — только к функциям-проекциям. Допуск ищется по имени
сеанса в `ac_trust.clearances` (уровень и категории на проект). Проекция показывает только то, что допуск покрывает,
включая сущности, в которые слиты упомянутые.

У восьми проекций ядра (досье, отчёт Проверки, провенанс, карточка оборудования, лента, сохранность, модель, пробелы
схемы) отказ всегда один и тот же («ACCESS_DENIED: нет допуска») — «нет такой записи» и «нельзя» неразличимы; у них
же есть параметр «на момент» и digest (sha256 JSON), ответ на прошлый момент воспроизводим. **Проекции наборов данных
(циклы 10–11) устроены иначе**: у них нет ни digest, ни параметра «на момент», а отказы различаются
(`CLEARANCE_INSUFFICIENT` с названием колонки, `REF_UNRESOLVED: строки с таким ключом нет`) — читатель с допуском в
проекте может отличить «нет строки» от «нельзя».

Роли базы: `ac_app` (приложение; член только `ac_loader`), `ac_loader` (INSERT в таблицы данных, UPDATE только двух
статусов), `ac_migrator` (исторический импорт, только позже печати истории), `ac_trust_admin` (реестр доверия),
`ac_modeler` (схема tenant), `ac_gateway` → `ac_storage` (реестр объектов хранилища), `ac_projector` (владелец
проекций, только SELECT), `ac_reader`.

## 9. Производители, публикации, оригиналы

**TechSense (S4, D17–D20).** Артефакт `umr-artifact/0.3` (узлы: сущность, величина, действие, условие, отношение;
якоря в байтах входов) сохраняется в базе по адресу sha256; квитанция подписывает адрес артефакта; база сама
разбирает артефакт и сверяет каждое утверждение с узлом. Один запуск — один артефакт и одна квитанция. Адаптер
детерминирован, сущности сопоставляет только по сильному ключу, всё неотображённое выносит в отчёт, а не теряет.
Отображаются четыре роли графа: `instance-of`, `part-of`, `has-parameter`, `requires-action`.

**Публикации Web Monitoring (S5, D21–D24).** Адрес публикации = sha256(JCS(tenant, издание, нормализованный текст)).
Заборы одной статьи (лишние пробелы, мобильная и AMP-версии, метки перехода в адресе) — рендеринги одной публикации;
они не перечисляются, а выводятся. Поддержка факта считается по публикациям, а не по заборам. Лента упоминаний не
раскрывает заборы чужих проектов.

**Объектное хранилище оригиналов (S5 ч.2, D26).** Текст источника — в базе; сырой оригинал (страница, PDF, скан) — в
S3-совместимом хранилище по sha256. Объект регистрируется только вместе с успешной проверкой чтением, в одной
транзакции, единственной ролью-шлюзом. Скрубер перечитывает объекты и ведёт неизменяемый журнал (`OK` / `MISSING` /
`CORRUPT`). Проекция «сохранность оригиналов» отвечает на момент времени. Доказательство-цитата от судьбы оригинала
не зависит.

## 10. Схема как данные (цикл 9, D27.1)

Tenant описывает свою предметную область **записями**, а не таблицами: `ClassDef` (класс под одним из десяти корней;
родитель; абстрактность; атрибуты с типом, единицей, кардинальностью, обязательностью; наследование вниз),
`LinkDef` (связь между классами — предикат `x.…`), `IdentifierDef` (тип идентификатора: схема, сила, приоритет,
формат как список сегментов — не регулярное выражение). Принадлежность сущности классу — обычное утверждение
`schema.is_a` с доказательством.

- Определение — цепочка версий; каждая версия отличается от предыдущей ровно одним допустимым изменением, тип
  изменения выводится из разницы версий и сверяется с заявленным. «Ломающее» изменение — новое определение.
- **Утверждение проверяется по схеме своего времени.** Старые утверждения после изменения схемы остаются верными.
- Физическая модель не меняется: ни одной таблицы на действие пользователя.
- «Конструктор модели» — пока клиент командной строки над теми же записями (`код/core/model_constructor.py`).

## 11. Наборы данных и доказательство-строка (циклы 10–11, D27.2–D27.4, проект решения)

Мотив: реестры (ЕГРЮЛ, телефонные базы, «30 тысяч баз» владельца) нельзя хранить как утверждения. Замер из документа
мнения (100 тыс. записей по 26 полей): широкая таблица — ≈690 байт на запись; запись целиком одним утверждением —
≈4,4 КБ (6–8×); **каждое поле отдельным утверждением, как устроено ядро, — ≈56 КБ на запись (80–110×)**. В цикле 10
строка реестра из 12 колонок заняла в широкой таблице ≈313 байт. Решение-проект: **одна логическая модель, три профиля хранения**
(утверждения / массив / внешний) под одной идентичностью, маркировкой и провенансом. Исполнен профиль «массив»:

- **Версия набора** — `Source` вида `DATASET_VERSION`; его байты — манифест: набор, версия, `previous`, колонки (имя,
  тип, **своя маркировка у каждой колонки**, схема идентификатора, предикат), ключ строки, колонки-идентификаторы
  субъекта, файлы строк по sha256 с корнем дерева хэшей каждого файла.
- **Хэш строки** — дерево Меркла по ячейкам с солью (соль выводится из секрета строки; секрет — HMAC от ключа набора и
  значений строки). Скрытая ячейка по своему листу не подбирается.
- **Доказательство `ROW`**: утверждение цитирует только нужные колонки (значение + соль), остальные представлены
  листьями; путь включения приводит строку к корню файла из манифеста. Проверяется без чтения файлов и без
  доверенного посредника. Маркировка утверждения ограничена только **процитированными** колонками: утверждение об
  адресе организации не несёт руководителя (персональные данные).
- Строка должна быть **о субъекте утверждения** (идентификаторы строки принадлежат ему) и **говорить то же** (значение
  колонки, объявленной для предиката, равно литералу).
- В базе: каталог версий, широкие таблицы (секция на версию) с «печатью» — после загрузки база пересчитывает хэш
  каждой строки и корень каждого файла и сверяет с манифестом; после печати изменение запрещено. Поиск по
  идентификатору, чтение строки и сборка доказательства — только через проекции с допуском.
- **«О ком строка» (цикл 11).** Если идентификаторы одной строки принадлежат двум сущностям проекта (ОГРН у одной,
  ИНН у другой), запись не отвергается: валидатор выдаёт предупреждение `ROW_SUBJECT_CONFLICT`, проекция — флаг
  `subject_conflict` (по допуску читателя). Конфликт снимается слиянием.
- **Актуальность строки (цикл 11).** Проекция идёт по цепочке версий и отвечает: `CURRENT`, `NOT_LOADED`,
  `UNCHANGED`, `CHANGED` (какие процитированные колонки), `CHANGED_ELSEWHERE`, `ABSENT`, `INCOMPARABLE`, `BRANCHED`.
- Поддержка факта: N версий одного набора — одна поддержка.

Ограничения доказательства-строки: оно доказывает субъект и объект, но не уточнения и не срок действия утверждения;
на строку нельзя опереть литерал `QUANTITY`, `MONEY`, `CLASS_REF` (типов колонок четыре); утверждения конвейера
(PIPELINE) на строках не сделаны — только утверждения аналитика. Вывод секрета строки через HMAC — соглашение
производителя версии: ни валидатор, ни база его не проверяют (проверяется только длина секрета). В тестовом мире ключ
набора — открытая константа, то есть скрытые ячейки демонстрационных строк открывает любой, у кого есть код.

Замер (синтетика по образцу ЕГРЮЛ, 8 млн строк, 2 ядра): сборка версии на Python — 1005 с; загрузка — 29 с; печать —
175 с; таблица 2,5 ГБ + индексы 0,78 ГБ; поиск по ИНН — 32 мс; проверка доказательства валидатором — 0,05 мс.
Замер делал автор; рецензент воспроизводил только 200 тыс. строк.

## 12. Время и одновременная запись

- Время записей ставит база. Время, входящее в адрес записи, принимается в окне [сейчас − 5 минут; сейчас].
  Исторический импорт — только особая роль и только позже «печати истории».
- Ответ проекции на момент ближе пяти минут к «сейчас» помечается предварительным.
- Стражи, от которых зависят уже выданные ответы, сериализуются советующими блокировками PostgreSQL по ключам;
  состояние читается **после** блокировки. Единый порядок взятия есть только у цепочки `check:` < `claim:` <
  `entity:` < `source:` (и `merge-into:` раньше `entity:`). Остальные ключи (`schema:`, `text:`, `object:`, `dsprev:`,
  ключи идентичности) общим порядком не связаны; `text:` и `source:` в двух триггерах берутся в противоположном
  порядке.
- **Запись ядра возможна только в READ COMMITTED** (цикл 11): в REPEATABLE READ и SERIALIZABLE снимок берётся до
  блокировки, и страж читает устаревшее. Страж изоляции стоит на всех 41 таблице.
- Ключ `entity:` берётся исключительно тем, что меняет сущность (слияние, вывод, решение об идентичности), и
  разделяемо тем, что на неё опирается (утверждение, Проверка, слияние в неё).
- Известное ограничение: взаимная блокировка возможна в двух названных сценариях; загрузчик обязан повторять
  транзакцию (сам загрузчик этого ещё не делает).
- Известные исключения из невозвратности и из «существование закрытого не раскрывается» (обе не исправлены кодом,
  записаны как ограничения): время печати версии набора ставится до фиксации транзакции, поэтому ответ на прошлый
  момент в этом окне может измениться (условие: транзакция загрузчика после печати короче пяти минут); проекция
  актуальности строки намеренно раскрывает, что между двумя доступными версиями есть закрытая.

## 13. Две реализации одних правил и что доказано

**Нормативный валидатор** (`код/core/validator.py`, Python, 1851 строка) — единственная нормативная реализация.
Фаза 0: сырые значения (целые в ±(2⁵³−1), без одиночных суррогатов, вложенность ≤ 64). Фаза 1: JSON Schema.
Фаза 2: семантика. 47 кодов ошибок (46 требуют негативный пример, один — предохранитель `VALIDATOR_INTERNAL_ERROR`)
и 4 кода предупреждений.

**База** (`код/slice/*.sql`, PostgreSQL 16): 41 таблица, 182 функции, 129 триггеров. Те же правила — ограничениями
и триггерами. Гарантируется совпадение «отказ / приём», а не кода: из 491 негативного вектора, отвергнутого базой,
код валидатора совпал у 406, остальные 85 отвергнуты другим кодом или ошибкой ограничения. У базы есть и собственные
коды (`CHECK_CLOSED`, `CLAIM_ABOUT_MERGED_ENTITY`, `ISOLATION_LEVEL_UNSUPPORTED`, `CLEARANCE_INSUFFICIENT` и др.).
Только за валидатором остаются: строгая форма записи и представление чисел JSON,

# 02. Методика: как это строится

Платформу строит языковая модель (Claude, роль «Главный-1» — главный архитектор и руководитель проекта) под
управлением одного человека — владельца. Ниже — как устроена работа, что считается доказательством и где методика
дала сбой. Исходная постановка — `приложения/управление/ПРОМПТ_ГЛАВНЫЙ-1_Архитектура_семантики_v1.md`.

## 1. Предыстория и главный поворот

До 30.09.2026 проект вёл чат ChatGPT. За ≈18 раундов он произвёл один документ — контракт слоя доверия (CM18, ≈890 КБ,
статус «предложено, не принято») — и ни строки исполняемого кода. Независимая проверка показала, что часть его
«доказательств» — тавтология (тесты проверяли генератор сам на себя; «аудит» искал слова в тексте).

Задача, поставленная новому руководителю: **перевести проект из режима «бесконечное уточнение документа» в режим
«исполняемое ядро + документ, который проверяется кодом»**. Контракт CM18 заморожен как справочный; ChatGPT оставлен
подчинённым чатом (в исполняемом ядре его частей нет; на 01.10 сдач от него не было).

## 2. Роли

| Кто | Что делает |
|---|---|
| **Владелец** (человек) | ставит цели, принимает решения, которые нельзя принять за него (модель данных D27, персональные данные, порядок работ), даёт команду «дальше». Очень занят: правило «владелец не курьер» — он не переносит тексты между чатами и не ищет файлы |
| **Главный-1** (Claude) | проектирует, пишет код, запускает, сам выбирает объём цикла, заказывает независимую рецензию, выносит вердикты на сдачи подчинённых, ведёт документы |
| **Независимый рецензент** (отдельный экземпляр Claude без истории создания) | атакует сдачу: читает код, пишет и запускает собственные скрипты, выносит вердикт. Прогонам автора не верит |
| **Подчинённые чаты** (ChatGPT) | выполняют задания по почте (папка на Google Drive, письма с шапкой и машиночитаемым блоком) |

## 3. Цикл

Единица работы — одна команда владельца «дальше» (один цикл, от полутора часов до суток машинного времени).

1. Главный-1 выбирает объём цикла из плана и списка открытого.
2. Проектирует и пишет: правило → код валидатора → негативный и позитивный векторы → мутант → то же правило в базе →
   атака в обход валидатора → при необходимости гонка двух транзакций.
3. Запускает собственные прогоны.
4. Отдаёт снимок кода **независимому рецензенту до объявления результата**.
5. Получает вердикт: **ПРИНЯТО / ПРИНЯТО С ЗАМЕЧАНИЯМИ / ВОЗВРАТ**. При возврате — исправляет, пишет ответ автора по
   каждой находке, отдаёт новый снимок. Раундов столько, сколько нужно. Так должно быть; отклонения — в §6.
6. Полные прогоны (все векторы, все мутанты, регрессия всех прежних срезов).
7. Документ «Архитектура ядра vN», файл передачи дел (handoff), публикация: GitHub (с проверкой `git ls-remote`),
   Google Drive, проект Claude.
8. Отчёт владельцу: коротко, по-русски, с абзацем «что достигнуто» простыми словами.

## 4. Что считается доказательством

**Правило проекта (сформулировано в первый день и расширялось):**

> Правило без кода и без негативного вектора правилом не считается.
> Условие, ослабление которого не ловит ни один вектор, считается непроверенным.
> Правило, заявленное «в базе», должно выдерживать атаку в обход валидатора.
> Правило о времени и закрытости должно выдерживать гонку двух транзакций.
> Новое правило добавляется только вместе с вектором и мутантом, которого этот вектор убивает.

Инструменты:

| Инструмент | Что это | Что ловит |
|---|---|---|
| **Вектор** | преобразование эталонного мира + ожидаемый **точный** набор кодов ошибок (и предупреждений) | правило не срабатывает или срабатывает лишнее |
| **Позитивный граничный вектор** | вход «на самой границе допустимого», который обязан пройти | правило слишком строгое |
| **Мутант** | одно ослабление или ужесточение одного условия валидатора; должен быть «убит» хотя бы одним вектором | условие, которое ничем не проверяется |
| **Эквивалентный мутант** | мутант, не меняющий ответ ни на одном входе; требует письменного обоснования | (сам по себе — риск: см. §6) |
| **Атака в обход валидатора** | SQL напрямую под ролью приложения, минуя загрузчик | база верит приложению |
| **Гонка** | две транзакции, вторая стартует, пока первая не зафиксирована | страж читает устаревшее состояние |
| **Паритет** | один и тот же вход — валидатору и базе; расхождение отказа и приёма недопустимо | две реализации разошлись |
| **Исчерпывающий паритет** | все кодовые точки Юникода через функции нормализации обеих сторон | расхождение на редком символе |
| **Дифференциальный фаззинг** | случайные повреждения манифестов и доказательств — обеим сторонам | расхождение на случайном входе |
| **Свидетель** | конкретный вход, опровергающий заявление «мутант эквивалентен» или «правило держит» | самообман автора |

Разделяются «документарное закрытие» и «исполняемое доказательство»; первое вторым не называется.
Числа в документах берутся из файлов вывода прогонов, не из памяти.

## 5. Независимая рецензия

- Рецензент — отдельный экземпляр модели, который **не видел, как делалась работа**. Он получает задание, снимок кода
  и адрес базы; работает на своих копиях и своих базах.
- Он обязан: проверить заявленное собственным перезапуском; написать свои атаки и свои мутанты; искать то, что
  автор не заявлял; сверить документ с кодом.
- Находки — с уровнем (P0 — нарушение гарантии; P1 — существенный дефект; P2 — замечание) и воспроизводящим скриптом.
- Вердикт выносится по списку находок. Автор отвечает на каждую: исправлено (где проверить) / не исправлено (почему,
  куда записано) / отклонено (рецензент решает, согласиться ли; один раз он согласился, понизив уровень находки).
- Скрипты рецензентов сохраняются. В автоматическую регрессию входят адаптированные атаки рецензентов только ранних
  циклов (S1, S22, S23, S24, S5); скрипты рецензентов S4, S6, S9, S10, S11 лежат в репозитории, но в регрессию не
  включены.

Что показала практика: **ни одна из десяти работ, отданных на рецензию, не прошла первый раунд целиком** (в двух
работах без возврата прошла часть «валидатор», а часть «база» возвращена), обычно с находками уровня P0, хотя все
собственные тесты автора проходили
(`03_ИСТОРИЯ_ЦИКЛОВ.md`). Собственные тесты автора систематически не находят то, что находит
посторонний.

## 7. Передача дел и память

Модель не помнит прошлых разговоров. Преемственность держится на файлах:

- **Handoff** (`АС_HANDOFF_ГГГГ-ММ-ДД_vNNN.md`) после каждого цикла: решения владельца, что сделано, что доказано,
  рецензия, что нужно от людей, открытое, где что лежит, уроки. Новый чат продолжает по одной фразе.
- **Архитектура ядра vN** — что именно сделано и чем отличается от предыдущей версии.
- **GitHub** — весь код, прогоны, отчёты и скрипты рецензентов.
- **Проект Claude** и **Google Drive** — дубли ключевых документов.

## 8. Как принимаются решения

- Решения нумеруются (D1…D27) и живут в документах архитектуры (`04_РЕШЕНИЯ.md`).
- Крупное решение оформляется как «мнение» с исследованием аналогов, измерением и вопросами владельцу; проходит
  независимую рецензию до показа владельцу (D27: три раунда).
- Если владелец не ответил, работа идёт «по проекту решения», это прямо пишется в каждом документе, отступления от
  текста проекта перечисляются.
- Перед обращением к людям — исчерпать исследование и проверку силами моделей; людям — только то, что модель решить
  не смогла.

## 9. Темп

Одиннадцать циклов за четверо суток (30.09–03.10.2026): от пустого места до ядра с базой, 681 вектором и 535
мутантами. Это одновременно сильная и слабая сторона методики — см. `05_СЛАБЫЕ_МЕСТА_И_ВОПРОСЫ.md`.

## 3. Наблюдения

1. **Ни одна из десяти работ не прошла первый раунд целиком** (онтология, срез, проекции, TechSense, публикации,
   хранилище, мнение D27, схема, наборы данных, цикл 11). Строки «v0.2», «S2.1» и «S24» в таблице — повторные раунды
   после возврата. В двух работах (S5, S6) без возврата прошла часть «валидатор», а часть «база» возвращена.
   Собственные тесты автора при этом всегда проходили.
2. **Рецензия находит дефекты прежних, уже «принятых» циклов.** В цикле 11 шесть из одиннадцати находок P0 относились
   к стражам, принятым в циклах 3–9. «Принято» означает «рецензент не нашёл», а не «дефектов нет».
3. **Исправление порождает новые находки.** В цикле 11 исправление взаимной блокировки (раунд 2) открыло обход
   решения «различны» (раунд 3).
4. **Классы дефектов повторяются:** время и «задним числом»; гонки двух транзакций; расхождение двух реализаций на
   редких символах Юникода; утечка существования закрытого объекта через побочный признак; правило, заявленное в
   документе, но не проверенное ни одним вектором.
5. **Число эквивалентных мутантов растёт медленно** (3 → 10), каждый обоснован письменно; заявленная эквивалентность
   опровергалась рецензентами четыре раза (пять мутантов).
6. **Не все повторные проверки делал рецензент.** В цикле 7 исправления перепроверил сам автор; последние замечания
   уровня P2 в циклах 10 и 11 и в проекте D27 исправлены после финального вердикта.

# 05. Слабые места, как их видит автор, и вопросы к критикам

Этот файл написан автором платформы против самого себя. Его задача — не защитить работу, а сэкономить критику время:
вот что автор уже знает, вот где он сам не уверен. Самое ценное — то, чего в этом списке **нет**.

## A. Слабые места, которые автор признаёт

### A1. Нет ни одного настоящего пользователя и ни одной настоящей записи
Всё проверено на синтетическом мире из ≈110 записей и синтетическом реестре «по образцу ЕГРЮЛ». Реальные графы
TechSense, реальная лента Web Monitoring, реальная выгрузка ЕГРЮЛ, реальные досье ни разу не загружались. Модель
данных шести продуктов придумана архитектором по описаниям владельца, без разговора с сотрудниками этих продуктов.
План-график от 01.10 предполагал реальные данные с цикла 5; их нет до сих пор, а циклы шли дальше.

### A2. Рецензент — та же модель, что и автор
«Независимый» рецензент не видел процесса создания, но это другой экземпляр того же Claude. Общие слепые пятна
вероятны. Вердикт «ПРИНЯТО» означает «этот рецензент за отведённое время не нашёл», и история показывает, что
следующий находит (в цикле 11 — шесть дефектов уровня P0 в частях, принятых раньше). В цикле 7 второго раунда не
было вовсе: исправления перепроверил сам автор.

### A3. Темп
Одиннадцать циклов за четверо суток. Ни одна из десяти работ не прошла первый раунд рецензии целиком, обычно из-за P0. Это можно читать как «процесс ловит
ошибки» или как «автор систематически сдаёт сырое, а качество держится на рецензенте». Автор не может отличить одно
от другого изнутри.

### A4. Две реализации одних правил
Нормативный валидатор на Python и стражи в PL/pgSQL (41 таблица, 182 функции, 129 триггеров). Паритет проверяется
тестами, но каждое новое правило пишется дважды, а расхождения находятся снова и снова (числа JSON, версии Юникода,
`true` ↔ `1`, даты до нашей эры). Альтернативы (одна реализация, вызываемая из базы; генерация одной из другой) всерьёз
не рассматривались.

### A5. Логика в триггерах и советующих блокировках
Гарантии держатся на порядке блокировок, который соблюдается по договорённости в коде (и единый порядок есть не у
всех ключей); на том, что все пишут в READ COMMITTED; на том, что функция, которая берёт блокировку и затем читает,
не помечена `STABLE`. Каждое из этих условий уже однажды было нарушено. Взаимная блокировка возможна, загрузчик обязан повторять транзакцию — и пока этого не делает.
Производительность под конкурентной нагрузкой не измерялась ни разу.

### A6. Цена
Запись реестра, разложенная по утверждению на поле, — ≈56 КБ (80–110× к широкой таблице); одним утверждением на
запись — ≈4,4 КБ. Чтение одного доказательства-строки — 6 мс, при цепочке из 60 версий —
50 мс, и это дважды на утверждение в досье. Нагрузочных испытаний нет. Сборка версии набора на Python — 2 минуты на
миллион строк. Полный мутационный прогон — около трёх часов на двух ядрах.

### A7. Собственные конструкции там, где есть стандарты
Собственный формат манифеста и файлов строк вместо Parquet / Iceberg (объяснение: в среде нет сети для установки).
Собственная конструкция «дерево Меркла по ячейкам с солью из HMAC» — криптограф её не смотрел, а вывод секрета
строки ничем не проверяется (это соглашение производителя версии). Собственный эмулятор
S3 вместо настоящего MinIO: клиент и эмулятор подписывают запросы одним кодом, общая ошибка была бы невидима.

### A8. Мутационное тестирование покрывает только валидатор
Мутируется Python-валидатор; стражи базы мутациям не подвергаются. Для базы есть атаки и паритет, но нет способа
узнать, какое условие триггера ничем не проверено.

### A9. Решение по модели данных не принято
Три цикла (9, 10, 11) построены на проекте решения D27, который владелец не утвердил. Отступления от текста проекта
накопились (четырнадцать по наборам данных, несколько по схеме, два в цикле 11). Если владелец решит иначе, часть работы придётся переделать.

### A10. Персональные данные
Архитектор предложил два механизма удаления (уничтожение ключа шифрования; запись «изъято по закону») и вынес выбор
владельцу. Владелец решил персональные данные не удалять. Поэтому механизмов стирания нет: журналы неизменяемы,
цитаты входят в адресуемые по содержимому утверждения. Правовое основание обработки и последствия этого решения для
права на удаление никто не оценивал.

### A11. Модель угроз неполна
Владелец базы данных — вне модели угроз. Одна роль загрузчика на все tenant. Подпись квитанции проверяет только
валидатор. Окно в пять минут для времени, входящего в адрес записи. Проверка «версия набора без файлов в хранилище»
принимается. Ключ набора (от него зависят соли) — где хранится и как меняется, не решено.

### A12. Память проекта — файлы передачи дел
Модель не помнит прошлых циклов; контекст сжимается. Один цикл (9) уже был объявлен завершённым без проверки, и
документ передачи дел утверждал неправду. Ничто, кроме дисциплины, не мешает этому повториться.

### A13. Расстояние до цели
Цель владельца — «аналог Palantir» и перевод шести продуктов на общее ядро. Сделано ядро данных. Нет ингеста,
интерфейсов, поиска, автоматического сопоставления сущностей, извлечения языковыми моделями, ролей пользователей,
развёртывания. Ни один продукт на ядро не переведён.

# 06. Словарь

| Слово | Значение в этом проекте |
|---|---|
| **Ядро** | общая модель данных шести продуктов: записи, правила, валидатор, база |
| **Tenant** | организация-владелец данных; граница источников, ключей доверия и схемы |
| **Проект** | область одного продукта внутри tenant; граница сущностей, утверждений и допусков |
| **Источник (Source)** | байты одного забора (документ, статья, выписка, версия набора данных), адрес — sha256 байтов |
| **Наблюдение** | факт получения источника: когда, откуда, кем |
| **Сущность (Entity)** | то, о чём говорят утверждения; хранит только идентичность |
| **Утверждение (Claim)** | «субъект — предикат — объект» с доказательством, автором, временем и маркировкой |
| **Доказательство** | цитата (байтовый диапазон источника), узел графа артефакта или строка версии набора данных |
| **Рецензия (ClaimReview)** | запись о статусе утверждения: принято, оспорено, опровергнуто, отозвано |
| **Проверка (Check)** | объект Compliance: субъект, профиль, итоги по измерениям, следы поиска |
| **След поиска** | запись о том, где, что, когда и кем искали; источник с результатом поиска к ней приложить можно, но не обязательно |
| **Квитанция (ArtifactReceipt, receipt)** | подписанная службой запись: какой артефакт, из каких входов, какие утверждения выпущены |
| **Артефакт** | результат работы службы-производителя (граф разбора TechSense), сохранённый по адресу sha256 |
| **Реестр доверия (trust anchors)** | ключи служб вне данных, которые эти ключи удостоверяют |
| **Маркировка** | уровень доступа + категории (персональные данные, коммерческая тайна, для служебного пользования) |
| **Допуск** | уровень и категории, выданные читателю на проект |
| **Проекция** | функция базы, которая строит ответ (досье, отчёт, карточку) только из того, что покрывает допуск читателя |
| **Digest** | sha256 ответа проекции; одинаков для одного вопроса на один момент времени (есть у восьми проекций ядра, у проекций наборов данных его нет) |
| **Скелет** | грубая нормальная форма имени для поиска двойников (латинская «о» = кириллическая «о») |
| **Сильный / слабый ключ** | идентификатор, однозначно называющий сущность (ИНН) / допускающий совпадение у разных (ФИО + дата) |
| **Слияние** | перевод сущности-дубля в статус MERGED с передачей ключей выжившей |
| **Публикация** | статья издания; объединяет заборы с одинаковым нормализованным текстом |
| **Рендеринг** | один забор публикации (обычная, мобильная, AMP-версия) |
| **Оригинал** | сырой файл источника в объектном хранилище |
| **Схема tenant** | классы, связи и типы идентификаторов, объявленные tenant как записи (`ClassDef`, `LinkDef`, `IdentifierDef`) |
| **Набор данных, версия набора** | реестр или справочник; версия — неизменяемый снимок с манифестом |
| **Манифест** | описание версии набора: колонки, ключ, файлы строк и корни их деревьев хэшей |
| **Печать версии** | пересчёт базой всех хэшей загруженных строк и сверка с манифестом; после неё строки неизменяемы |
| **Валидатор** | нормативная программа проверки набора записей (Python) |
| **Страж** | триггер или функция базы, проверяющая то же правило, что валидатор |
| **Срез (slice, S1…S11)** | исполнение части ядра на PostgreSQL вместе с тестами и атаками |
| **Вектор** | пример входа с ожидаемым точным ответом валидатора |
| **Мутант** | намеренно испорченная копия валидатора; должен быть «убит» вектором |
| **Эквивалентный мутант** | мутант, не меняющий ответ ни на одном входе |
| **Атака** | попытка нарушить правило в обход валидатора, напрямую в базе |
| **Гонка** | проверка правила при двух одновременных транзакциях |
| **Паритет** | совпадение ответов валидатора и базы на одном входе |
| **Свидетель** | конкретный вход, опровергающий заявление автора |
| **P0 / P1 / P2** | уровни находок рецензии: нарушена гарантия / существенный дефект / замечание |
| **Цикл** | работа по одной команде владельца «дальше», от проектирования до публикации |
| **Handoff** | файл передачи дел между чатами |
| **Главный-1** | роль Claude: главный архитектор и руководитель проекта |
| **D1…D27** | нумерованные решения архитектуры |
| **CM18** | прежний контракт слоя доверия, написанный до начала этой работы; заморожен |
| **JCS** | RFC 8785, каноническая форма JSON; от неё считаются адреса записей |
| **UMR** | Uniform Meaning Representation — формат смыслового графа TechSense |
