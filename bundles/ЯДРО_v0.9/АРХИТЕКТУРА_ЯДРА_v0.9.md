## 2. Версия набора данных

`Source{source_kind: DATASET_VERSION, media_type: application/vnd.ac.dataset-manifest+json, schema_version:
core-ontology/0.4}`; его байты — **манифест** `ac-dataset-manifest/0.1` в канонической форме RFC 8785:

| Поле | Смысл | Кто читает |
|---|---|---|
| `dataset_id` (`dst_…`) | семейство версий | `previous`; поддержка факта (N версий одного набора — одна поддержка) |
| `tenant_id` | равен tenant источника | валидатор, триггер регистрации |
| `version_label` | имя версии | проекции |
| `previous` | адрес предыдущей версии | если такой источник известен в tenant — он версия того же набора |
| `columns[]`: `name`, `type` (`STRING`/`INTEGER`/`BOOLEAN`/`DATE`), `marking`, `identifier_scheme`?, `predicate`? | схема строки; маркировка — у каждой колонки своя | типы ячеек; маркировка утверждения; связь «утверждение ↔ строка»; индекс идентификаторов |
| `key[]` | объявленный ключ строки; пусто — строка называется своим хэшем | `row_key`; единственность ключа в версии |
| `subject[]` | колонки-идентификаторы сущности, о которой строка | связь строки с субъектом утверждения |
| `row_count`, `files[]`: `object`, `byte_length`, `rows`, `rows_root` | файлы строк по адресу sha256 и корень дерева строк каждого файла | проверка включения; проверка файла, если он есть в хранилище |

Правила манифеста (код `DATASET_MANIFEST_INVALID`): JSON в UTF-8 без повторов ключей, целочисленный профиль, схема,
каноническая форма; имена колонок уникальны; ключ и `subject` — из колонок (`subject` — из колонок-идентификаторов);
`row_count` = сумма строк файлов; схема идентификатора — только у строковой колонки; tenant манифеста = tenant
источника; `previous`, известный в tenant, — версия того же набора; колонка объявляется для предиката реестра или схемы
tenant, определённого не позже первого наблюдения версии; файл версии, который есть в хранилище объектов, соответствует
манифесту (адрес, длина, каноническая строка `{h, k, s, v}`, типы, 16-байтный секрет, ключ, хэш каждой строки, корень;
ключ встречается в версии один раз).

Источник другого tenant для этого tenant неизвестен (в том числе как `previous`).

## 3. Хэш строки и доказательство

```
соль ячейки  = sha256(0x03 ‖ секрет строки (16 байт) ‖ имя колонки)
лист ячейки  = sha256(0x00 ‖ соль ‖ JCS([имя колонки, значение]))
узел         = sha256(0x01 ‖ левый ‖ правый)            (форма дерева RFC 6962)
хэш строки   = корень дерева листьев ячеек в порядке колонок манифеста
лист строки  = sha256(0x02 ‖ хэш строки);   корень файла = корень дерева листьев строк
секрет строки = HMAC-SHA256(ключ набора, JCS([dataset_id, все значения строки]))[:16]   (соглашение производителя)
```

Ключ набора — 32 случайных байта у загрузчика, не публикуется. Без него скрытая ячейка не подбирается по листу.
Неизменившаяся строка имеет тот же хэш в любой версии; строка, в которой изменилась любая ячейка, получает новые соли
всех ячеек — по листьям двух версий видно только «строка та же / не та же». **В тестовом мире ключ набора — константа
`DEMO_DATASET_KEY` в `core/fixtures.py`: мир воспроизводим, а скрытые ячейки демонстрационных строк открывает любой,
у кого есть этот файл.**

Доказательство `ROW` в теле утверждения: `{kind: "ROW", source_id, row_key?, row_sha256, cells[], proof{file, index,
hashes[]}}`. Ячейка — либо `{name, value, salt}` (процитирована), либо `{name, leaf}` (скрыта). Правила
(`EVIDENCE_ROW_INVALID`):

1. источник — версия набора с годным манифестом;
2. ячейки — ровно колонки манифеста в их порядке; значение процитированной ячейки — типа колонки;
3. корень дерева ячеек равен `row_sha256`;
4. путь включения приводит лист строки к `rows_root` файла `proof.file` при числе строк этого файла (RFC 9162 §2.1.3.2);
5. колонки ключа процитированы, `row_key` равен их значениям как JSON; у набора без ключа `row_key` нет;
6. **строка — о субъекте утверждения**: набор объявляет `subject`; хотя бы один процитированный идентификатор субъекта
   строки принадлежит субъекту утверждения на момент утверждения (с учётом слияний к этому моменту), и ни один не
   расходится с идентификатором субъекта той же схемы. Набор без `subject` утверждений не подтверждает;
7. **утверждение говорит то, что в строке**: процитирована колонка, объявленная для предиката утверждения, и её
   значение равно литералу (для колонки-идентификатора — литерал `IDENTIFIER` той же схемы; для объекта-сущности —
   ячейка называет идентификатор этой сущности на момент утверждения);
8. маркировка утверждения доминирует маркировку каждой ПРОЦИТИРОВАННОЙ колонки (`MARKING_BROADER_THAN_INPUT`); скрытые
   колонки её не ограничивают — утверждение об адресе организации не несёт руководителя.

Что доказательство-строка **не** доказывает: уточнения (`qualifiers`) и срок действия утверждения — это заявление
автора утверждения, как и при доказательстве-цитате. В проекциях у такой строки стоит `proves: [subject, object]`.

Пометки записей: `DATASET_VERSION` и утверждение с доказательством `ROW` — только в записи `core-ontology/0.4`;
словарь 0.3 допустим в записи 0.3 или 0.4; прежние записи остаются 0.2/0.3 (их адреса не изменились). Набор записей,
объявленный 0.3, записей 0.4 не несёт.

## 4. PostgreSQL (`slice/ddl_s10.sql`, правки `slice/ddl_s1.sql`)

- `ac.claim_evidence` получила `kind` (`SPAN`/`ROW`) и `row_ev`; строки доказательств по-прежнему порождаются только
  триггером из тела утверждения, и строка равна элементу тела (RS-02 расширено на вторую форму).
- `ac.datasets` — каталог версий; строка появляется только из триггера при записи байтов манифеста.
- `ac.row_evidence_guard` — те же правила 1–8, что в валидаторе. Арифметика (JCS строки для каждого символа Юникода,
  листья, корни, пути включения) сверена с Python исчерпывающе (S10-02).
- Проверки, зависящие от ДРУГИХ записей (`previous`, предикаты колонок), выполняются при фиксации транзакции в любом
  порядке прихода; такие записи пишутся только в `READ COMMITTED` (иначе `ISOLATION_LEVEL_UNSUPPORTED`): проверке нужен
  снимок, взятый после блокировки.
- Широкие таблицы (схема `acd`): одна таблица на (tenant, набор, состав колонок), секция на версию;
  `ac.dataset_open` → `COPY` → `ac.dataset_seal`. Печать пересчитывает хэш КАЖДОЙ строки из типизированных ячеек,
  корень КАЖДОГО файла, число и номера строк, единственность ключа, профиль значений (дата 0001…9999, целое в ±(2^53−1))
  и сравнивает с манифестом. После печати DML запрещён любой роли (DDL владельца базы — вне модели угроз).
  Неудачную незапечатанную загрузку сбрасывает `ac.dataset_reset`.
- Читатель (таблиц не видит): `ac.dataset_row` — строка, колонки выше допуска названы в `withheld`;
  `ac.dataset_find` — поиск по идентификатору по запечатанным версиям (ключ строки — только если читатель допущен к
  колонкам ключа, иначе хэш строки); `ac.dataset_evidence` — доказательство `ROW`, собранное базой; `ac.dataset_info` —
  колонки и файлы версии. Существует ли версия, читателю без допуска не сообщается.
- Поддержка факта: N версий одного набора — одна поддержка (`ac.support_key`).

Названные исключения паритета «база ↔ валидатор»: файлы строк база не читает (её проверка строк — печать таблицы);
в частности, манифест с длиной файла, не равной длине объекта, пришедшего в хранилище ПОЗЖЕ манифеста, в базе остаётся
(валидатор его отвергает), а `ac.dataset_info` показывает `LENGTH_MISMATCH`;
конверта набора записей в базе нет; правило «после слияния пишут о выжившем» есть только у базы (как и раньше).

## 7. Отступления от проекта D27.2–D27.4

1. Доказательство несёт путь включения и самодостаточно; пути через шлюз (`ac.dataset_row_checks`) и блокировки по ключу
   строки нет. Причина: «база выше заявления» выполняется по манифесту без чтения файлов и без доверенного посредника.
2. Соль ячейки — sha256(0x03 ‖ секрет ‖ имя), не HMAC; секрет строки — не случайный, а HMAC(ключ набора, [набор, значения строки]).
3. Лист ячейки включает имя колонки; префиксы 0x00/0x01/0x02 разделяют лист ячейки, узел и лист строки.
4. Маркировка источника-версии — маркировка манифеста (схемы), **не максимум по колонкам**; колонки маркируются
   отдельно. Иначе любое утверждение из набора с одной колонкой персональных данных несло бы эту категорию.
5. Корень Меркла — на файл, не один на версию; доказательство позиционное (файл, номер строки).
6. Доказательство несёт листья всех скрытых колонок: 150 колонок — ≈14 тыс. знаков, 512 — ≈46 тыс. Сжатия нет.
7. Литерал утверждения сверяется с одной колонкой, объявленной для предиката, а не «литерал = все процитированные».
8. Уточнения и срок действия утверждения со строкой не сверяются (см. §3).
9. Файлы строк — JSON Lines, не колоночные. Удалённых ключей и дельт нет.
10. Широкие таблицы: секционирование по версии и b-tree; **BRIN и RLS не делались**; признака «индексируемый» нет —
    индекс идентификаторов строится у каждой запечатанной версии.
11. Поле `subject` манифеста — в проекте его нет.
12. У набора без ключа одинаковых строк быть не может (строка называется своим хэшем): телефонная база с настоящими
    дубликатами строк должна получить ключ или колонку-номер.
13. На строку нельзя опереть утверждение с литералом `QUANTITY`, `MONEY` или `CLASS_REF`: типов колонок четыре
    (`STRING`, `INTEGER`, `BOOLEAN`, `DATE`), а литерал сверяется с колонкой того же типа.
14. Семейство набора для подсчёта поддержки — самоназванный `dataset_id`: тот же реестр под другим `dataset_id`
    считается другой поддержкой, а чужой набор с тем же `dataset_id` — той же. Это заявление tenant, как издание у
    публикации.
