## 3. Находки

Формат: где → минимальная атака (скрипт, id) → наблюдаемый вывод → исправление. Все атаки на БД выполнены под `SET SESSION AUTHORIZATION ac_loader`, живой режим, с COMMIT.

### RS-01 P0 — БД не гарантирует «одна сущность в проекте»: ключи идентичности отделены от сущности и изменяемы
- **Где:** `ddl_s1.sql:210-250`: у `entity_keys` триггер только `BEFORE INSERT`; `:673`: GRANT INSERT, UPDATE, DELETE для ac_loader. Сущность вставляется без ключей (`:148-205`), тип ключа не сверяется с типом владельца, значения ключей из `identity` не выводятся.
- **Атака:** `db_attacks.py` D01, D02, D03.
  - D01: `DELETE FROM ac.entity_keys WHERE owner_entity_id='ent_d_developer'`, затем вторая карточка с тем же ОГРН и ИНН → `COMMIT | ACTIVE с ОГРН 1215000007310 в prj_dossier: 2`.
  - D02: `INSERT INTO ac.entities …` копия Ломова без строк ключей → `ACTIVE с ИНН 695203141810: 2`.
  - D03: `UPDATE entity_keys SET value='x'` и поддельный `ru.inn`, чтобы `told_apart` сработал → `владельцев ключа ФИО+дата Ломова: 2`.
- **Почему P0:** заявление «identity keys unique in DB» держится, только если пишущий сам честно вычислил и записал ключи. 33 отказа `ENTITY_DUPLICATE_IN_PROJECT` в db_vectors получены только потому, что ключи вычисляет нормативный загрузчик.
- **Исправление:**
  - Отозвать у ac_loader UPDATE и DELETE на `entity_keys`. Перенос ключей при слиянии делать функцией `SECURITY DEFINER`.
  - Добавить отложенную проверку при COMMIT. У каждой сущности должен быть хотя бы один ключ. `entity_type` ключа должен совпадать с типом владельца. Сильные ключи, которые извлекаются без нормализации (`inn`, `ogrn`, `ogrnip`, `inn|kpp`, `vin`, `imo`, кадастровый номер как числа), БД должна вычислять из `identity` сама и сверять с переданными строками.
  - Нормализацию имён перенести в SQL-функцию с общими с валидатором векторами (или в PL/Python) — только тогда ключ действительно «держится базой».

### RS-02 P0 — провенанс: доказательство, которого нет в теле утверждения, вписывается в обход `pg_trigger_depth()`
- **Где:** `ddl_s1.sql:340`: `IF pg_trigger_depth() < 2`. У ac_loader есть право TEMP на базу.
- **Атака:** D05. Создаются `CREATE TEMP TABLE t`, функция `pg_temp.inj()` и `CREATE TRIGGER … ON t`, которые делают `INSERT INTO ac.claim_evidence` (ord=99) для утверждения о дате рождения Ломова с цитатой из источника по китам. Затем `INSERT INTO t`. Результат: `COMMIT | доказательств в теле: 1, строк claim_evidence: 2, цитата ord=99 в проекции: Синий кит — вид усатых китов`. Проекция `claim_provenance`, на которой строится S3, показывает подложную цитату как `verified`.
- **Исправление:**
  - В `evidence_guard` требовать, чтобы строка совпадала с элементом тела `c.body->'evidence'->NEW.ord` (source_id, span, quote_sha256, quote, graph_node), и чтобы `NEW.ord < jsonb_array_length(c.body->'evidence')`.
  - Дополнительно отозвать INSERT на `claim_evidence` у ac_loader. `claims_after` сделать `SECURITY DEFINER`.
  - По возможности отозвать TEMP у роли приложения.

### RS-03 P0 — Проверка: путь «IN_PROGRESS → UPDATE COMPLETED» обходит неретроактивность, маркировку и субъект
- **Где:**
  - `ddl_s1.sql:512`: `CHECK_CLAIM_NOT_ACCEPTED_AT_COMPLETION` проверяется только при вставке связи, если Проверка **уже** COMPLETED.
  - `:499-501`: в живом режиме в закрытую Проверку утверждения добавлять нельзя. Значит, это единственный живой путь, и на нём правило не действует никогда.
  - `:436-467`: UPDATE открытой Проверки может менять `marking` (сверяется только с субъектом), `subject_entity_id`, `profile`, `requested_at`, `as_of`.
  - `:553-580`: `check_complete` не перепроверяет статус утверждений, отношение к субъекту и доминирование.
- **Атака:**
  - D09: утверждение REFUTED, Проверка IN_PROGRESS → FOUND → `UPDATE … COMPLETED`. Результат: `chk_rs09: COMPLETED, статус утверждения на момент завершения = REFUTED`.
  - D10: утверждение RESTRICTED привязано, затем маркировка Проверки понижена до CONFIDENTIAL и Проверка завершена. Результат: `Проверка CONFIDENTIAL […] COMPLETED, утверждение RESTRICTED, dominates=false`.
  - D11 (P1-часть): после привязки субъект заменён на ent_k_lomov. Результат: `субъект Проверки ent_k_lomov, субъект утверждения ent_k_developer`.
- **Исправление:**
  - В отложенном `check_complete` для COMPLETED перепроверять каждую связь: `status_at(claim, completed_at)='ACCEPTED'`, отношение к субъекту (с учётом слияний), `dominates(k.marking, c.marking)` и доминирование над источниками результатов поиска.
  - UPDATE Проверки разрешить только для колонок перехода статуса. `marking`, `subject_entity_id`, `profile`, `requested_at`, `as_of` и `previous_check_id` сделать неизменяемыми.

### RS-04 P0 — маркировки и байты источников изменяемы
- **Где:** `ddl_s1.sql:100-127`: у `sources` триггеров нет; у `source_bytes` guard только на INSERT; GRANT UPDATE, DELETE — `:673`.
- **Атака:**
  - D06: `UPDATE ac.sources SET marking=RESTRICTED…` для источников вики и `SET marking=PUBLIC` для всех CONFIDENTIAL. Результат: `доказательств, где утверждение шире источника: 3; CONFIDENTIAL-источников осталось: 0` — рассекречивание источников с ПДн без следа.
  - D07 (P1-часть): `DELETE FROM ac.source_bytes …` и `UPDATE byte_length`. Результат: `доказательств без байтов: 12 из 32; источников с byte_length <> длины байтов: 8`.
- **Исправление:**
  - `sources` и `source_bytes` сделать append-only (триггер `forbid` на UPDATE и DELETE).
  - Смену маркировки оформлять новой записью с перепроверкой доминирования всех зависящих утверждений и Проверок.
  - Удаление байтов по 152-ФЗ (O2) делать отдельной процедурой с записью-надгробием, чтобы проекция явно показывала «байты уничтожены», а не молча теряла строки.

## 4. Проверено и держится

- **Роль ac_loader при `SET SESSION AUTHORIZATION`:** не может `SET ROLE ac_migrator`, `session_replication_role`, `TRUNCATE`, `ALTER TABLE … DISABLE TRIGGER`, CREATE в `public` и `ac`. Не может писать в `ac_trust.keys` (DB-A39).
- **Append-only:** UPDATE и DELETE на `claims`, `claim_evidence`, `claim_reviews`, `artifact_receipts`, `receipt_*`, `check_findings`, `check_finding_claims` запрещены. Удаление сущностей и Проверок тоже.
- **Сущности:** `identity`, тип, проект и маркировка неизменяемы. Переход статуса возможен только один, из ACTIVE.
- **Время:** `recorded_at` у рецензии и `status_changed_at` штампуются базой.
- **Доказательства при штатной вставке:** проверяются sha256, границы UTF-8 и `quote`.
- **Receipt:** один receipt на PIPELINE-утверждение (UNIQUE и отложенный триггер).
- **Эквивалентные мутанты:** M001, M005, M006, M317 и M318 действительно эквивалентны.
- **Контрольные атаки в валидаторе держатся:** греческая ο, U+034F, U+FE0F, U+3164, U+2212, полноширинные формы, латинские a/e/o в названии неформальной группы (B1-08, B1-09, B3-04). Держится и граница RR-01 «строго позже» (B4-03, B4-04).
