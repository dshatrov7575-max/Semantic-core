## Находки P0

### S11R-01. Конфликт сильных ключей обходится порядком записи

**Сделано.** Организация A с ОГРН строки зафиксирована. Затем одной транзакцией `ac_loader` в READ COMMITTED: утверждение о A с процитированным ИНН строки (`recorded_at` — время писателя), следом организация B с этим ИНН. Вариант (a) в `a02`: B вставлена в одном сеансе и не зафиксирована, утверждение фиксируется в другом, затем фиксируется B.

**Получено.** Оба варианта приняты. В базе `created_at` B = 10:32:41.23 (начало транзакции), `recorded_at` утверждения = 10:32:43, то есть B существовала к моменту утверждения. Валидатор на мире, выгруженном из базы: `EVIDENCE_ROW_INVALID` («строка называет идентификатор другой сущности проекта»). `ac.evidence_json` по принятому утверждению: `verified = false`. `ac.dataset_subject`: CONFLICT. То же утверждение, записанное после фиксации B, база отвергает.

**Должно быть.** База отвергает то, что отвергает валидатор; принятое утверждение остаётся `verified`.

**Причина.** `created_at` сущности — `now()` (начало транзакции), `recorded_at` утверждения — время писателя, более позднее. Запись сущности с сильным ключом и запись утверждения на строке не сериализованы: общей блокировки по ключу нет.

**Исправление.** Блокировка `ac.lock_keys` по каждому сильному ключу (проект, тип, схема, значение) в обеих записях: при вставке сущности и при записи утверждения по каждому процитированному идентификатору субъекта строки. Время создания сущности читать после блокировки (`ac.guarded_time`), а не `now()`.

### S11R-05. Цепочка слияний в READ COMMITTED

**Сделано.** Сеанс 1: вставка D сразу в статусе MERGED → A, фиксация через 3 с. Сеанс 2: `UPDATE` A → MERGED в B.

**Получено.** Оба COMMIT. В базе `ent_r5_d: MERGED → ent_r5_a`, `ent_r5_a: MERGED → ent_r5_b`. Ключ `ru.inn = 5001000027` принадлежит слитой `ent_r5_a`. Валидатор: `ENTITY_MERGE_INVALID`. Последовательно то же база отвергает («цепочки слияний запрещены»).

**Причина.** `ac.entities_guard` берёт блокировку `entity:` только в ветке UPDATE; вставка в статусе MERGED проверяет цель без блокировки.

**Исправление.** В ветке INSERT со статусом MERGED брать `ac.lock_keys('entity:' || merged_into)` до `ac.merge_ok`.

### S11R-06. «Различны» и слияние одной пары

**Сделано.** Сеанс 1: слияние P → Q, фиксация через 3 с. Сеанс 2: решение DISTINCT(P, Q), фиксация сразу.

**Получено.** Оба COMMIT. Валидатор: `IDENTITY_DECISION_INVALID` («решено „различны“, но сущности слиты»). Последовательно база отвергает.

**Причина.** `ac.identity_decisions_complete` (отложенная, при COMMIT) и `ac.distinct_decided` в страже слияния читают без общей блокировки.

**Исправление.** В `ac.identity_decisions_guard` для DISTINCT брать `ac.lock_keys` по `entity:` обеих сущностей — тот же ключ, что берёт слияние.

### S11R-07. Открытая публикация с закрытым рендерингом

**Сделано.** Источник S1 (PUBLIC) зафиксирован. (a) Сеанс 1 вставляет S2 — другой забор того же текста с того же издания, CONFIDENTIAL, фиксация через 3 с; сеанс 2 фиксирует публикацию PUBLIC. (b) Одной транзакцией: публикация, затем S2.

**Получено.** Оба варианта приняты. Рендеринг CONFIDENTIAL получен 10:38:23.68, `recorded_at` публикации 10:38:25. Валидатор: `MARKING_BROADER_THAN_INPUT`. Последовательно база отвергает.

**Причина.** `ac.publications_guard` блокирует ключи `source:` только тех источников с этим текстом, которые видит. Источник, который пишется параллельно или позже в той же транзакции, получает `observed_at = now()` и оказывается «полученным к `recorded_at`».

**Исправление.** Блокировка по ключу текста (`text:tenant/text_digest`) в `ac.publications_guard` и в `ac.source_texts_after`; время наблюдения читать после неё; при появлении рендеринга перепроверять маркировку уже записанных публикаций этого текста и издания.

### S11R-08. Утверждение и удаление его предиката в одну секунду

**Сделано.** В начале секунды загрузчик записывает утверждение `x.max_length` о синем ките; сразу после конструктор модели записывает версию 3 класса `sdf_whale_species` с `REMOVE_ATTRIBUTE`.

**Получено.** Оба приняты. Версия 3 записана 10:50:54, утверждение записано 10:50:54, принято базой в 10:50:54.05. Валидатор: `PREDICATE_UNKNOWN`. То же утверждение секундой позже база отвергает.

**Причина.** `ac.schema_version_guard` округляет время версии вниз до секунды; проверка «не позже уже записанных утверждений схемы» работает только при историческом импорте.

**Исправление.** Время версии — следующая целая секунда после блокировки (округление вверх с ожиданием) либо отказ, если в tenant есть утверждение схемы с `recorded_at` не раньше времени версии, в том числе вживую.

### S11R-10. `ac.dataset_subject` выдаёт закрытую сущность

**Сделано.** В проекте есть организация с ОГРН строки (видимая читателю `ac_rd_cs`). Добавлена организация с ИНН этой строки, маркировка с категорией ПД, которой у читателя нет.

**Получено.** До: `ONE [ent_r3_trub]`. После: `CONFLICT [ent_r3_trub]` — один владелец в списке. Читатель с полным допуском видит обоих. Досье закрытой сущности тому же читателю: `ACCESS_DENIED`.

**Должно быть.** Читатель без допуска не получает факта существования.

**Причина.** Статус считается подзапросом по всем владельцам ключей, список `owners` — только по видимым.

**Исправление.** Считать статус по тому же отфильтрованному набору, что и список.

То же утверждение с `recorded_at` между созданием первой и второй организации (в пределах пятиминутного окна) принято базой и валидатором; `verified = true`, `ac.dataset_subject` — CONFLICT. Исправление: вживую проверять носителей ещё и на текущий момент, как `ac.is_instance_now` в цикле 9.

### S11R-03. Ретроактивность через исторический импорт

Утверждение с ИНН строки принято, `verified = true`. Мигратор создаёт организацию с этим ИНН временем раньше утверждения (после печати истории) — принято. `verified` становится `false`, валидатор на мире из базы: `EVIDENCE_ROW_INVALID`. Исправление: при историческом импорте сущности отвергать время создания не позже `recorded_at` утверждений, цитирующих её сильный ключ у другого субъекта.

### S11R-04. Утверждение о слитой сущности

Сеанс 1 сливает X, фиксация через 3 с; сеанс 2 фиксирует утверждение о X. Оба COMMIT; слита 10:37:06.47, утверждение записано 10:37:08. Последовательно: `CLAIM_ABOUT_MERGED_ENTITY`. Правило есть только в базе, паритет не нарушен. Исправление: `ac.claims_before` берёт `ac.lock_keys` по `entity:` субъекта и объекта до чтения статуса.

### S11R-09. Идентификатор строки не нормализуется

Вектор автора NS03, меняется только запись LEI — одна и та же строка символов в ячейке и в `foreign_ids` чужой организации.

| Запись LEI | Валидатор | База | Ключ сущности | `dataset_subject` |
|---|---|---|---|---|
| `549300123456` | `EVIDENCE_ROW_INVALID` | отвергнуто | — | — |
| `5493-0012-3456` | принял | принято | `549300123456` | ONE |
| `5493ab123456` | `EVIDENCE_ROW_INVALID` | отвергнуто | — | — |
| `5493AB123456` | принял | принято | `5493ab123456` | ONE |

Настоящие LEI пишутся заглавными буквами, поэтому для них не работает ни правило конфликта, ни проверка «строка о субъекте». Исправление: приводить значение ячейки-идентификатора той же функцией нормализации схемы, что и ключ сущности, на обеих сторонах и в проекции; вектор и мутант.

### S11R-11. Смена типа ключа роняет досье

Версия 1: ключ `code` типа STRING, утверждение на строке `A-1`. Версия 2 того же набора: `code` типа INTEGER. После печати версии 2 `ac.dossier` сущности: `ERROR: invalid input syntax for type bigint: "A-1"`. Досье на момент до печати читается. Версия запечатана навсегда, поэтому отказ постоянный. Причина: `ac.row_currency` сравнивает только имена ключа, `ac.dataset_cells` приводит значение к типу колонки новой версии. Исправление: сравнивать имена и типы ключевых колонок, при различии — INCOMPARABLE; ошибку расчёта актуальности не поднимать в досье.

### S11R-12. «Последняя» версия — по первому наблюдению

Утверждение на версии `2026-10-01`: CURRENT. После дозагрузки архивной версии `2025-01-01`: `CHANGED [address]`, «последняя» — архив. С честной цепочкой `previous` (утверждение на вершине `2026-10-02`) и дозагрузкой архива 2024 года: ABSENT. Функция `ac.row_currency` поле `previous` не читает (`a70_static.sh`: 0 вхождений). Исправление: «последняя» — вершина цепочки `previous`, начинающейся от версии утверждения; версия вне цепочки — INCOMPARABLE или отдельный статус.

### S11R-13. Невоспроизводимость ответа на прошлый момент

Печать версии 2 выполнена в открытой транзакции (`sealed_at` = 10:43:44.24), момент t = 10:43:46.23, фиксация позже. Прочитано в момент t: `currency = CURRENT`, digest досье `sha256:e4098833…`. Прочитано позже на тот же t: `CHANGED`, digest `sha256:34611304…`. Тот же класс, что S6R-01. Исправление: время печати ставить под блокировкой, которую берёт и читатель (как `ac.custody`), либо считать версию видимой по времени фиксации.

### S11R-14. `NOT_AVAILABLE` выдаёт закрытую версию

Читатель `ac_rd_cs` видит в досье `CURRENT`. После загрузки версии с маркировкой RESTRICTED — `NOT_AVAILABLE`. На прямой вопрос о закрытой версии (`ac.dataset_info`) он получает `ACCESS_DENIED`, неотличимый от «нет такой версии». Статус заявлен в задании, но противоречит правилу 4. Исправление: считать актуальность по последней версии, доступной при маркировке утверждения.

### S11R-15. Части правила без вектора

Штатные мутанты, мой прогон: MS01, MS02, MS03, MS06, MS07 и MR40…MR47 — убиты все 13. MS02 («сущности других проектов считаются») убит PS04, вектором о времени создания: отдельного вектора «носитель в другом проекте» нет, мутанта убивает случайное совпадение с эталонным миром. MS06 убит эталонным миром.

Свои мутанты нового правила, полный прогон по всем векторам:

| Мутант | Что изменено | Итог |
|---|---|---|
| X01 | граница `<=` → `<` (носитель создан ровно в момент утверждения) | выжил |
| X02 | носитель в статусе RETIRED не считается | выжил |
| X03 | носитель, слитый в третью сущность, не считается | выжил |
| X04 | проверяется только первый чужой идентификатор | выжил |
| X05 | носитель с категорией ПД не считается | выжил |
| X06 | считается только носитель, созданный до субъекта | выжил |

X05 — не часть заявленного правила, в счёт не идёт. Остальные пять — поведение, которое код реализует и которое ни один вектор не закрепляет. Атака автора C04 проверяет RETIRED только в базе. Исправление: по вектору на каждую часть.

   | 0,1 % / 0,05 % / 0,05 % | 64 | 79 % | 88,1 % | 88,0 % |

   | 0,01 % / 0,005 % / 0,005 % | 512 | 83 % | 90,5 % | 90,3 % |

2. **Один прогон.** Строка «0,1 %, файл 4096: 0,8 %» — шум: по пяти зёрнам 1,6 / 1,6 / 1,6 / 1,2 / 0,0 %, аналитика (1−u)^C = 1,7 %.
3. **«Устойчива только резка по корзинам» — неверно.** Границы файлов по содержимому (граница там, где хэш ключа делится на C, строки остаются в порядке ключа) дают при 0,1 % / 0,05 % / 0,05 % и C = 64 общих 88,7 % файлов и 78,8 % строк против 0,2 % у позиционной резки. Порядок по ключу сохраняется, что нужно для доказательства невхождения из варианта (в).

Выводы 1 и 2 о позиционной резке и рекомендация (а) остаются верными. Исправление: число корзин = N/C; несколько зёрен; строка о границах по содержимому; предел манифеста и цена чтения — в выводы.
