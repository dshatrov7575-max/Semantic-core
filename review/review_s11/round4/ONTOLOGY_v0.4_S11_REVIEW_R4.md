### S11R4-01. Неназначенный символ в названии неформальной организации

**Сделано.** Неформальная организация с названием «Гр» + U+1E030 и пометкой `ddd`. Набор с колонкой, объявленной идентификатором схемы `org.informal`; в строке значение `гра|ddd` (обычная кириллическая «а»). Утверждение о ней цитирует эту колонку.

**Получено.** Ключ сущности у валидатора — `гр` + U+1E030 + `|ddd`, в базе — `гра|ddd`. Валидатор: `EVIDENCE_ROW_INVALID` («ни один процитированный идентификатор субъекта строки не принадлежит ему»). База: принято. Обратный мир (в строке запись, как у сущности): валидатор принял, база отвергла.

**Должно быть.** База отвергает то, что отвергает валидатор.

**Причина.** Запрет раунда 3 стоит на `foreign_ids` и `registration`. Ключ `org.informal` — `norm(name)|disambiguator`, а `norm` включает NFKC; название — свободный текст. База нормализует по Юникоду 15, валидатор — по 14.0. Класс символов у сторон одинаков (`d02` W3: 1 112 063 кодовые точки, расхождений 0) — расходится нормализация.

**Исправление.** Одно правило: identity сущности с символом, не назначенным в Юникоде валидатора, в любом строковом поле отвергается — в валидаторе и в `ac.identity_keys` (проверка `ac.has_unassigned` по всем значениям identity). Вектор на `name`. Это же закроет расхождение ключей для полей, которые я не проверял (метка оборудования, название понятия).

Находка узкая: нужны экзотический символ в названии и набор, объявивший колонку со схемой `org.informal`. Но это третий раунд одного класса, и направление — запрещённое правилом 1.

### S11R4-02. MS23 не эквивалентен

Обоснование автора: ключ сущности не содержит неназначенных символов. Это верно только для двух полей. Свидетель: та же неформальная организация, в строке «ГР» + U+1E030 + `|ddd`. Валидатор — `EVIDENCE_ROW_INVALID`, мутант MS23 принимает. После исправления S11R4-01 обоснование станет верным; до него мутант выживший.

Свой мутант Z01 (`any` → `all` в `_has_unassigned`) теперь убит вектором NS14.

### S11R4-03. Архитектурный документ

Записи о S11R3-04, S11R3-05, S11R-13, S11R-21 / S11R2-10 сделаны честно: числа (6 мс и 50 мс на доказательство), условие «транзакция после печати короче пяти минут», намеренное раскрытие связи версий — совпадают с кодом и моими замерами. Утверждения разделов 1–5 и 8 сверены с кодом; расхождения:

1. **§2, взаимные блокировки.** Назван один сценарий («опереться на сущность, затем изменить её»). Второй: два сеанса, каждый сливает по две сущности в цели T и U в противоположном порядке, — `deadlock detected` на ключах `merge-into:` (`d01` T4). Формулировку стоит обобщить: повтор по `40P01` обязателен для любой транзакции с несколькими записями о сущностях.
2. **§3, «у сущности идентификатор с неназначенным символом отвергается».** Верно для `foreign_ids` и `registration`; следующая из этого фраза «иначе стороны расходятся» кодом не подтверждена (S11R4-01).
3. **§3, флаг `subject_conflict`.** Не сказано, что сеанс без допуска в проекте — суперпользователь — видит все конфликты, а прочие роли без допуска получают ответ по маркировке утверждения (`ac.conflict_clearance`).
4. **§4, `changed_columns`: «названы доступные читателю».** Код называет колонки, которые доминирует маркировка утверждения, а не допуск читателя.

## Атаки на изменённое

**Ключ `merge-into:`** (`d01_merge_into.py`):

| Сценарий | Итог |
|---|---|
| A → T открыто / T → U | второе: `ENTITY_MERGE_INVALID` (цепочки) |
| T → U открыто / A → T | второе: `ENTITY_MERGE_INVALID` (цель не ACTIVE) |
| A → T открыто / вывод T | оба приняты; T выведена после слияния — допустимое состояние |
| вывод T открыт / A → T | второе: `ENTITY_MERGE_INVALID` |
| вставка D сразу слитой в T / T → U, оба порядка | второе отвергнуто |
| «различны»(C, D): C → A / D → A | второе: `IDENTITY_DECISION_INVALID` |
| утверждение о цели + слияние дубля в неё, два сеанса | оба приняты (S11R2-05 не вернулась) |

Сущностей, слитых в слитую или в выведенную раньше слияния, после всех гонок 0.

**Запрет неназначенных символов.** Класс у валидатора и базы совпадает на всех кодовых точках. `validator.row_id` и `ac.row_id`: 28 770 пар, расхождений 0. Обход через другое поле identity — S11R4-01.
