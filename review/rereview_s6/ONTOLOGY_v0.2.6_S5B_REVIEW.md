## Замечания

### S6R-01 — P0 — ответ `ac.custody` на прошедший момент меняется задним числом (поздняя фиксация проверки)

Нарушено: п. 5 «ответ на момент t не меняется, когда бы его ни спросили позже».

Причина: `checked_at := clock_timestamp()` ставится в момент INSERT, а видимой строка становится в момент COMMIT.
Между ними проекция на момент `as_of ≥ checked_at` строку не видит; после фиксации — видит. Никакой блокировки
или «водяной отметки» у журнала проверок нет (у закрытия Проверок это решено ключом `source:` — D14/D22; здесь нет).

Воспроизведение: `db_attacks.py`, блок A1 (транзакция шлюза открыта 10 с, проекция спрошена на 5-й секунде и снова
после фиксации, с одним и тем же `as_of`):

```
journal: OK@00:48:24.294841, CORRUPT@00:51:54.919584
asked at T2=00:51:59.92139 (scrub tx open):   as_of=…21:51:59.92139 originals=[('…/zarechye','OK',1)]      digest=sha256:c037708587a
asked AGAIN for the same as_of after commit:  as_of=…21:51:59.92139 originals=[('…/zarechye','CORRUPT',2)] digest=sha256:cf8bd957db5
RESULT: FINDING — same as_of, different answer
```

Почему важно: проекция выдаёт дайджест; два документа «сохранность на 21:51:59» с разными дайджестами и разным
состоянием оригинала («цел» / «повреждён») — ровно то, что гарантия исключает. Окно не мало: `gateway.scrub`
пишет все результаты одной сессией, а при регистрации время проверки ставится раньше фиксации всегда.

Исправление: время проверки должно быть не раньше момента, когда строка становится видимой. Варианты: (а) перед
вставкой брать тот же advisory-ключ, что и читатель (`object:<tenant>/<addr>`), а проекции ограничивать `as_of`
моментом «нет открытых писателей» (горизонт: `least(as_of, min(xact_start) открытых транзакций, пишущих реестр)`);
(б) проще — отдавать ответы только на `as_of ≤ clock_timestamp() − Δ` и запретить транзакции шлюза длиннее Δ
(`SET LOCAL transaction_timeout`/`idle_in_transaction_session_timeout` для роли `ac_storage`); (в) хранить
`xmin`-независимую отметку фиксации (отдельная таблица «горизонт реестра», продвигаемая после COMMIT) и
отвечать только до неё.

### S6R-03 — P1 — `ac.custody` раскрывает заборы других проектов: адрес, время и оригинал чужого наблюдения

Нарушено: п. 5 «не раскрывает того, чего читателю видеть нельзя» (и решение D24: чужие заборы в ленте не показываются).

Источник общий для tenant; наблюдение не имеет ни проекта, ни грифа. Проекция выводит ВСЕ наблюдения источника
(`origin_uri`, `observed_at`, адрес/тип/размер оригинала), включая сделанные после записи утверждения и в интересах
другого проекта. Лента (`wm_feed`) показывает только адреса издания публикации, провенанс — только время первого наблюдения.

Воспроизведение: `db_attacks.py`, блок A4 — загрузчик добавляет к источнику, на который ссылается открытое
утверждение `prj_wm_region`, наблюдение с адресом `https://intranet.corp.example/cases/4471/target-ivanov?token=SECRET`
и PDF-оригиналом; читатель `ac_rd_wm` (допуск PUBLIC, только `prj_wm_region`):

```
reader ac_rd_wm … sees in custody: [{"original": {"checks": 1, "object": "sha256:a8ecbd6d…", "status": "OK", …
  "media_type": "application/pdf", "byte_length": 4242, …}, "origin_uri": "https://intranet.corp.examp…
same URI in wm_feed (D24): False | in provenance: False | custody marking label: {'level': 'PUBLIC', 'categories': []}
RESULT: FINDING — custody discloses what feed/provenance do not
```

Почему важно: адрес забора выдаёт предмет чужой работы (внутренний адрес, параметры запроса, токены), документ при
этом помечен PUBLIC. Исправление: показывать только наблюдения, поступившие не позже `recorded_at` утверждения
(те, на которые оно могло опираться), либо только первое; а правильнее — дать наблюдению проект-владелец и
показывать наблюдения своего проекта (для остальных — только счётчик без адресов).

### S6R-04 — P1 — гонка «проверка ↔ наблюдение»: принято наблюдение на оригинал, последняя проверка которого — не «цел»

Нарушено: п. 3 «наблюдение может назвать только объект … чья последняя проверка OK».

`ac.observation_original_guard` читает журнал без блокировки; незафиксированная запись MISSING/CORRUPT не видна.
Воспроизведение: `db_attacks.py`, блок A3 (в зафиксированной истории проверка MISSING РАНЬШЕ наблюдения):

```
observation insert while MISSING was uncommitted: ACCEPTED
committed history: check MISSING@00:53:08.224294 ; check OK@00:53:07.875835 ; observation ingested@00:53:13.229811
observations whose original was NOT OK at their own ingestion time (invariant of claim 3): 1 -> FINDING
locks … an observation insert would wait on (pg_locks, this db, not granted): 0
```

Исправление: в обоих триггерах (`object_checks_guard` и `observation_original_guard`) брать
`ac.lock_keys(ARRAY['object:' || tenant || '/' || addr])` ДО чтения часов и журнала — как сделано для `source:`.
Это же закрывает половину S6R-01.

### S6R-05 — P1 — любая ошибка хранилища записывается в неизменяемый журнал как «утрачен»

Нарушено: п. 4 «check возвращает OK/MISSING/CORRUPT» по существу (MISSING = «объекта нет»), п. 5 (журнал — факты).

`ObjectStore.check` ловит `ObjectStoreError` и возвращает `MISSING`; `S3Backend.get` бросает `ObjectStoreError` на
любой статус, кроме 200/404 (403 при истёкшем ключе или расхождении часов, 500/503, 301). Один запуск проверки с
неверным секретом объявляет утраченными все оригиналы tenant; записи стереть нельзя; новые наблюдения на целые
объекты отвергаются до следующей удачной проверки; `ac.custody` на этот интервал навсегда показывает «утрачен».

Воспроизведение: `store_attacks.py`, блок B1:

```
the object is intact on disk: True
scrub with a rejected signature (HTTP 403 for every GET) returned: {'OK': 0, 'MISSING': 2, 'CORRUPT': 0}
journal: OK,MISSING
consequence: observation naming the intact original: ERROR:  ORIGINAL_INVALID: оригинал повреждён или утрачен по последней проверке
```

То же на ложном сервере без базы (`store_attacks2.py`):

```
HTTP 503 SlowDown                                                       -> check() = MISSING
HTTP 404 NoSuchBucket (wrong bucket name in the gateway configuration)  -> check() = MISSING
connection dropped after half of the body (Content-Length says full)    -> check() = raises ChunkedEncodingError
```

(обрыв соединения даёт исключение, и обход прерывается без записи — это правильное поведение; 503 и неверное
имя бакета — нет).

Исправление: MISSING только при подтверждённом 404 NoSuchKey (и отдельной проверке, что бакет существует — иначе
NoSuchBucket тоже даст «утрачен»); всё остальное — исключение, запуск проверки прерывается без записи (или четвёртый
результат `UNREACHABLE`, не влияющий на приём наблюдений).

### S6R-06 — P1 — шлюз работает в сеансе суперпользователя; роль `ac_storage` его не ограничивает

Нарушено: п. 3 и докстринг шлюза «The gateway never sees claims or source texts (role ac_storage can only read and
append the registry)».

`gateway._psql` подключается как `PGUSER` и выполняет `SET SESSION AUTHORIZATION ac_storage`; это возможно только
суперпользователю, а отменяется одной командой. Роль `ac_storage` — NOLOGIN, ни одна роль с входом в неё не входит,
то есть другого способа запустить шлюз в текущем виде нет. Атаки D606–D606c автора проверяют роль, а не шлюз.

Воспроизведение: `store_attacks.py`, блок B3:

```
through gateway._psql: now postgres, superuser=on, source_bytes rows readable=15, claims=30
login roles that are members of ac_storage: 0
scrub(tenant=<payload>) under python3 (default): AssertionError | injected table exists: no
scrub(tenant=<payload>) under python3 -O: {'OK': 0, 'MISSING': 0, 'CORRUPT': 0} | injected table exists: postgres/30
```

Вторая половина — SQL-инъекция: значения подставляются в текст SQL в долларовых кавычках с постоянной меткой
`$gw$`, единственная защита — `assert`, который исчезает при `python3 -O`; аргумент `tenant` в `scrub()` до базы не
проходит `object_key`. В сеансе суперпользователя инъекция — это полный доступ к базе.

Исправление: отдельная роль с входом (`ac_gateway LOGIN IN ROLE ac_storage NOINHERIT` + `SET ROLE` либо прямые
права), шлюз подключается ею; параметры — через `psql -v` + `:'name'` либо драйвер с параметрами; проверку метки —
`if … raise`, не `assert`; tenant проверять `object_key`-правилом в начале `scrub`.

### S6R-07 — P1 — исторический загрузчик объявляет объекты «сохранёнными и проверенными чтением» без хранилища

Нарушено: п. 3 «приложение не может объявить объект сохранённым; объект регистрируется только вместе с успешной
проверкой чтением».

`load_s1.py` (строки с `SET ROLE ac_storage`) сам вставляет строку `ac.objects` и проверку `OK` для каждого
оригинала набора; к хранилищу он не обращается вовсе (байты берутся из словаря `content` валидатора). В реестре
появляется «проверка чтением», которой не было: `stored_by=postgres`, `checked_by=postgres`. Тест S6-01 автора
обходит это, вручную кладя объект в хранилище перед первой проверкой.

Воспроизведение: свежая база после `load_s1.py` — `SELECT * FROM ac.objects` →
`tnt_demo|sha256:7253d9f1…|679|…|postgres`; затем `store_attacks.py`, B1/B5: первая же проверка с исправным
хранилищем даёт для этого объекта MISSING (в B5: `{'OK': 2, 'MISSING': 1, 'CORRUPT': 1}` — MISSING это он).

Исправление: загрузчик должен вызывать `gateway.register(store, tenant, content[addr], media_type)` и не иметь
`SET ROLE ac_storage` в своём SQL; либо регистрировать исторические объекты отдельным результатом (например,
`DECLARED`), который не считается «цел» до первой проверки.

### S6R-08 — P2 — время проверки в журнале — время записи результата, а не чтения объекта

`gateway.scrub` сначала читает все объекты, потом одной пачкой пишет результаты; `checked_at` ставит база при
вставке. Объект, повреждённый после чтения, но до конца обхода, получает «цел» с временем ПОСЛЕ повреждения.
`store_attacks.py`, B4: `object damaged at 00:54:43.07843 | journal says: OK checked_at=00:54:46.153431 | really now: CORRUPT`.
На большом хранилище окно — часы; при сбое в середине обхода теряются все результаты. Исправление: писать результат
сразу после чтения каждого объекта; хранить два времени (начало чтения — от шлюза, запись — от базы).

### S6R-09 — P2 — в реестре нет ограничений на tenant; одна «кривая» строка навсегда ломает общий обход

`ac.objects.tenant_id` — произвольный текст (нет ни шаблона, ни связи с проектами): принимаются `tnt_ghost`,
`TNT/../tnt_demo`, строка с табуляцией (`db_attacks.py`, A5). Шлюз разбирает вывод `psql` по табуляции:
`store_attacks.py`, B5 — `scrub of everything raises: ValueError too many values to unpack`; строку удалить нельзя.
Для tenant, который не проходит `object_key`, обход пишет MISSING. Попутно: `ac_loader` читает реестр всех tenant
(`db_attacks2.py`, C3: `5|1`) — адрес объекта есть хеш содержимого, то есть приложение одного tenant может
проверить, хранит ли другой tenant известный ему документ; построчной защиты (RLS) нет. Исправление: `CHECK (tenant_id ~ '^tnt_[a-z0-9_]{2,64}$')`
на `ac.objects`; в шлюзе — формат вывода, не зависящий от содержимого (JSON построчно).

### S6R-10 — P2 — клиент S3: расхождения с настоящим S3, невидимые для собственного эмулятора

1. Узел с явным стандартным портом (`http://host:80`, `https://host:443`): в подпись идёт `host:80`, а библиотека
   отправляет `Host: host` → 403 SignatureDoesNotMatch на каждый запрос (B2), что вместе с S6R-05 даёт «утрачен» для всего.
2. Канонический запрос сортирует параметры по исходным именам, а не по закодированным (B7: `DIFFERENT` для имён
   `a~` / `aé`). Для нынешних трёх параметров неважно; для любого нового — ошибка подписи.
3. Запись без условия (`If-None-Match: *` не посылается): «никогда не перезаписывает» — это чтение-затем-запись,
   между ними окно; версионирование/блокировка объектов не требуются и не проверяются.
4. Эмулятор проверяет подпись ТЕМ ЖЕ `sigv4_signature`, что и клиент (импортирует его) — общая ошибка
   канонизации не обнаруживается в принципе. Эмулятор также принимает любой регион в области действия ключа
   и дату запроса 2000 года (B8: HTTP 200 в обоих случаях; настоящий S3: 400 AuthorizationHeaderMalformed и
   403 RequestTimeTooSkewed) — то есть регион по умолчанию `us-east-1` и расхождение часов не проверены ничем.
5. Эмулятор: выход за пределы бакета — `GET /originals/../originals2/secret.txt` → HTTP 200 (B8): `fpath()`
   сравнивает строки-префиксы (`…/originals` — префикс `…/originals2`).

Исправление: подписывать тот `Host`, который реально уйдёт (убирать стандартный порт); сортировать закодированные
пары; посылать `If-None-Match: *`; проверку подписи в эмуляторе написать независимо; прогон на настоящем MinIO —
обязательное условие приёмки этой части (автор сам указал, что его не было).

### S6R-11 — P2 — изоляция tenant «по префиксу ключа»: перечисление по префиксу без разделителя захватывает соседа

`keys("tnt_a")` возвращает и ключи `tnt_ab/…` (B6, оба бэкенда). В шлюзе `keys()` пока не используется, но это
единственный способ перечисления, и он не принимает tenant, а принимает сырой префикс. Кроме того, `object_key`
допускает tenant, запрещённые схемой (`sha256`, `_`, `0`). Исправление: `keys(tenant)` с обязательным `tenant + "/"`,
tenant — по шаблону схемы.

### S6R-12 — P2 — векторы не замечают трёх ослаблений правила ORIGINAL_INVALID

`val_mutants.py` (собственные мутанты валидатора против всех векторов автора):

```
R1 SURVIVED          проверяется оригинал только первого наблюдения
R2 KILLED by N702    длина: достаточно, чтобы объект был не короче заявленного
R3 SURVIVED          длина: достаточно, чтобы объект был не длиннее заявленного
R4 SURVIVED          оригинал проверяется только у источников с текстом в хранилище
```

Сам валидатор правило исполняет; дыра — в наборе векторов (N700–N702 бьют только по `observations[0]` источника с
текстом и только в одну сторону по длине). Исправление: три вектора — плохой оригинал у второго наблюдения;
заявленная длина меньше фактической; плохой оригинал у источника без байтов текста; и мутанты M703–M705 к ним.

## Что атаковано и НЕ сломано

Валидатор и схема (`val_attacks.py`):

- права: у `ac_loader`, `ac_migrator`, `ac_reader`, PUBLIC нет записи в реестр; у `ac_storage` — только SELECT/INSERT
  по трём столбцам двух таблиц, нет TEMP/CREATE, нет доступа к функциям проекций; владельцы таблиц — postgres;
- время и автора ставит база; UPDATE/DELETE отвергаются; объект без проверки OK в той же транзакции отвергается;
- совпадение времени в первичном ключе журнала: 200 000 проверок одного объекта одним оператором — 200 002
  различных `checked_at` (столкновений нет);
- границы: `bigint` — 2^63−1 принят, 2^63 отвергнут (валидатор 2^63 тоже отвергает); шаблон типа содержимого в базе
  совпадает с валидатором на всех пробах, включая перевод строки и кириллическую «е»;
- отказы проекции одинаковы (нет допуска, неизвестное утверждение, момент до записи, `-infinity`), `ac_storage` и
  `ac_loader` проекцию вызвать не могут;
- отчёты закрытых Проверок: дайджесты `check_report` до и после всех атак совпадают;
- прежние проекции (`check_report`, `provenance`, `dossier`, `wm_feed`, `equipment_card`) на одном и том же мире с
  `ddl_s5b.sql` и без него: 476 пар «вызов × читатель», 65 ответов, единственное различие — `evaluated_at`
  черновика незавершённой Проверки (текущее время); отказы совпали (`regress_projections.py`);
- регистрация объекта без уцелевшей проверки OK через точку сохранения и `SET CONSTRAINTS … IMMEDIATE` с откатом
  проверки — отвергнута при фиксации (`db_attacks2.py`, C1);
- `ac_loader` и `ac_migrator` не могут `SET ROLE ac_storage`; UPDATE наблюдения запрещён; оригинал без длины,
  длина без объекта, один тип, отрицательная длина — отвергнуты (C3, C4);
- доказательство по байтам не зависит от оригинала (п. 6): `evidence_json` читает только `ac.source_bytes`, при
  оригинале с последней проверкой CORRUPT провенанс утверждения по-прежнему `verified = true`
  (`proof_independent.out`, база `review062`), дайджесты отчётов те же (A8).

Хранилище (`store_attacks.py`): tenant с `/`, `..`, заглавными, `-`, переводом строки, пустой — отвергаются
`object_key`; подпись V4 совпала с независимой реализацией для PUT объекта, LIST с префиксом и токеном
продолжения (`+ / = пробел ~ *`), ключей с пробелом, `+`, `%`, юникодом.

## Не подтверждено (подозрения без воспроизведения)

- Шаг системных часов назад (NTP): проверка получит `checked_at` раньше предыдущей, и «последней» окажется не
  последняя записанная; часы сервера не трогал.
- Перенаправления 301/307 (другой регион AWS): `requests` идёт по ним, заголовок авторизации для нового узла
  недействителен → 403 → «утрачен» (частный случай S6R-05).
- `FsBackend.put` не делает `fsync`: проверка чтением читает кэш страниц; при отказе питания объект
  зарегистрирован и «проверен», но на диске пуст.
- Объекты больше нескольких ГБ: один PUT и чтение целиком в память при каждой проверке.
